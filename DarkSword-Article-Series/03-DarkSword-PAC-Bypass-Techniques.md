## 1. 引言

### 1.1 研究背景

指针认证码（Pointer Authentication Code, PAC）是 ARM 架构在 ARMv8.3 中引入的一项重要安全特性，旨在防御控制流劫持攻击。Apple 从 A12 芯片（iPhone XS/XR 系列）开始在其 SoC 中实现了 PAC 支持，并在 iOS 系统中广泛使用 PAC 来保护函数指针、返回地址和关键数据结构。

PAC 的引入极大地改变了 iOS 内核攻击的面貌。传统的 ROP/JOP 攻击技术因为需要有效的 PAC 签名而变得极其困难。然而，安全研究人员陆续发现了多种绕过 PAC 的方法，包括 PACMAN、XPAC 等攻击技术。

DarkSword 框架在其攻击链中集成了多种 PAC 绕过技术，使其能够在支持 PAC 的 iOS 设备上实现完整的攻击链。本文从防御视角深入分析这些技术的原理和检测方法。

### 1.2 研究范围

本文涵盖以下技术领域：

- ARM PAC 技术的架构原理和实现细节
- iOS 系统中 PAC 的具体使用方式
- PACMAN 侧信道攻击的原理和变体
- XPAC 非规范指针攻击技术
- 基于信息泄露的 PAC 绕过方法
- DarkSword 框架中的 PAC 绕过实现
- 检测和防御 PAC 绕过攻击的方法

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| PAC | Pointer Authentication Code，指针认证码 |
| PACIA | PAC Instruction for Authentication，指针认证指令 |
| PACIB | PAC Instruction for Authentication (B key)，B 密钥认证指令 |
| AUTIA | Authenticate Instruction，指针验证指令 |
| AUTIB | Authenticate Instruction (B key)，B 密钥验证指令 |
| XPAC | eXtended PAC，利用指针高位扩展的 PAC 攻击 |
| PACMAN | PAC Masking Attack，利用内存一致性协议的 PAC 攻击 |
| KTRR | Kernel Text Relic Protection，内核代码段保护 |
| PPL | Page Protection Layer，页面保护层的缩写 |

## 2. ARM 指针认证码技术详解

### 2.1 PAC 架构原理

PAC 通过在指针的高位中嵌入认证码来验证指针的完整性。当指针被用于关键操作（如函数调用、返回）之前，系统会验证嵌入的认证码是否正确。

#### 2.1.1 指针格式

在 ARM64 架构中，64 位指针并非使用全部 64 位：

```
64 位指针格式:
┌─────────────────────────────────────────────────┐
│  高位未使用位（TBI）  │     有效地址位           │
│  (用于 PAC 存储)       │     (实际地址)           │
├────────────────────────┤────────────────────────┤
│  Bit 63-55 (9 bits)    │  Bit 54-0 (55 bits)    │
│  或 Bit 63-56          │  或 Bit 55-0            │
└─────────────────────────────────────────────────┘

注: TBI (Top Byte Ignore) 位原本被忽略，PAC 利用这些位存储认证码
```

#### 2.1.2 认证密钥

ARM PAC 使用两组独立的密钥：

```
密钥层次结构:
├── APIAKey (Instruction A Key)
│   ├── 用于代码段指针认证
│   ├── 保护返回地址
│   ├── 保护函数指针
│   └── 由 EL3 安全固件管理
├── APIBKey (Instruction B Key)
│   ├── 备用指令密钥
│   ├── 用于特定场景的指针认证
│   └── 独立于 A Key
├── APDAKey (Data A Key)
│   ├── 用于数据段指针认证
│   ├── 保护数据指针
│   ├── 保护链表指针
│   └── 由 EL3 安全固件管理
└── APDBKey (Data B Key)
    ├── 备用数据密钥
    ├── 用于特权级别指针
    └── 独立于 A Key
```

#### 2.1.3 认证算法

PAC 的计算基于 QARMA 密码算法：

```
PAC 计算流程:
┌──────────────────────────────────────────┐
│  输入:                                    │
│  - 指针值 (64 bit)                        │
│  - 上下文值 (Context, 如 SP 或 LR)        │
│  - 密钥 (128 bit)                         │
├──────────────────────────────────────────┤
│  计算:                                    │
│  PAC = QARMA(Pointer, Context, Key)       │
│  结果: PAC 值 (通常 16-32 bit)            │
├──────────────────────────────────────────┤
│  输出:                                    │
│  认证指针 = Pointer | (PAC << 低位地址)    │
└──────────────────────────────────────────┘
```

### 2.2 PAC 指令集

#### 2.2.1 认证指令

```
PAC 指令分类:
├── 计算指令
│   ├── PACIA: 使用 A Key 计算指针认证码
│   ├── PACIB: 使用 B Key 计算指针认证码
│   ├── PACDA: 使用 Data A Key 计算认证码
│   ├── PACGA: 计算两个值的通用认证码
│   └── PACIA1716: 使用固定上下文的简化版本
├── 验证指令
│   ├── AUTIA: 使用 A Key 验证指针认证码
│   ├── AUTIB: 使用 B Key 验证指针认证码
│   ├── AUTDA: 使用 Data A Key 验证认证码
│   └── AUTIA1716: 使用固定上下文的简化验证
├── 剥离指令
│   ├── XPACI: 剥离指令认证码（保留指针值）
│   ├── XPACD: 剥离数据认证码（保留指针值）
│   └── 注: 剥离不等于验证，剥离后的指针可能无效
└── 控制指令
    ├── ERET: 异常返回时自动验证返回地址
    ├── RETAA: 使用 A Key 验证并返回
    ├── RETAB: 使用 B Key 验证并返回
    ├── BLRAA: 使用 A Key 验证并链接跳转
    └── BLRAB: 使用 B Key 验证并链接跳转
```

### 2.3 PAC 安全保证

#### 2.3.1 安全强度分析

```
PAC 安全参数:
├── 认证码长度
│   ├── 理论最大: 32 bit（取决于可用高位数）
│   ├── 实际使用: 约 16-24 bit
│   └── 安全强度: 2^16 到 2^24 次尝试
├── 暴力破解可行性
│   ├── 16 bit PAC: 65536 次尝试（约 1 秒）
│   ├── 20 bit PAC: 约 100 万次尝试（约 15 秒）
│   ├── 24 bit PAC: 约 1600 万次尝试（约 4 分钟）
│   └── 注: 实际时间取决于验证失败后的处理
├── 密钥隔离
│   ├── 用户态和内核态使用不同密钥
│   ├── EL1 和 EL2 使用不同密钥
│   └── 密钥存储在安全寄存器中
└── 上下文绑定
    ├── 可以将 SP 作为上下文（防止跨栈帧重用）
    ├── 可以将 PC 作为上下文（防止跨位置重用）
    └── 上下文绑定增加了重放攻击的难度
```

#### 2.3.2 已知弱点

1. **认证码长度有限**: 可用的高位数有限，导致认证码长度受限
2. **无认证剥离**: XPACI/XPACD 可以在不验证的情况下剥离 PAC
3. **密钥共享**: 同一特权级别的所有代码共享相同的密钥
4. **确定性**: 相同输入总是产生相同的 PAC 输出
5. **无时效性**: PAC 不包含时间戳或计数器

## 4. PACMAN 攻击深度分析

### 4.1 PACMAN 攻击原理

PACMAN 攻击是由 MIT 研究人员于 2022 年发现的一种针对 ARM PAC 的侧信道攻击。其核心思想是利用内存一致性协议的侧信道来暴力猜测 PAC 值。

#### 4.1.1 攻击模型

```
PACMAN 攻击模型:
┌─────────────────────────────────────────────┐
│                攻击场景                       │
├─────────────────────────────────────────────┤
│  前提条件:                                    │
│  1. 攻击者已拥有任意写原语                     │
│  2. 攻击者可以修改受 PAC 保护的指针            │
│  3. 系统使用指针组合器（Pointer Combiner）     │
├─────────────────────────────────────────────┤
│  攻击目标:                                    │
│  - 找到正确的 PAC 值，使伪造指针通过验证       │
├─────────────────────────────────────────────┤
│  攻击方法:                                    │
│  - 遍历所有可能的 PAC 值                      │
│  - 利用内存一致性侧信道检测验证成功/失败       │
│  - 当验证成功时，获得有效的认证指针            │
└─────────────────────────────────────────────┘
```

#### 4.1.2 指针组合器（Pointer Combiner, PC）

指针组合器是 PACMAN 攻击的关键组件：

```
指针组合器工作原理:
├── 功能
│   ├── 将指针值与 PAC 值组合
│   ├── 在验证时检查 PAC 是否正确
│   └── 验证结果影响后续操作
├── 侧信道泄露
│   ├── 验证成功: 指针正常用于内存访问
│   ├── 验证失败: 触发异常或指针被清零
│   └── 差异可通过缓存侧信道检测
├── 关键实现细节
│   ├── PC 在地址转换流水线中工作
│   ├── 验证结果影响 TLB 行为
│   └── 缓存状态反映验证结果
└── 攻击利用
    ├── 修改指针值和 PAC 猜测值
    ├── 触发指针组合器验证
    ├── 通过 Prime+Probe 检测缓存状态
    └── 确定 PAC 验证是否成功
```

### 4.2 PACMAN 攻击流程

```
PACMAN 攻击详细流程:

阶段一: 准备工作
├── 获取任意写原语（通过其他漏洞）
├── 定位目标指针在内核内存中的位置
├── 准备侧信道检测环境（缓存预热）
└── 确定 PAC 位的位置和长度

阶段二: 暴力猜测
├── 对于每个可能的 PAC 值:
│   ├── 1. 将猜测的 PAC 值写入指针高位
│   ├── 2. 触发指针组合器验证
│   ├── 3. 执行缓存探测（Prime+Probe）
│   ├── 4. 分析缓存状态
│   │   ├── 缓存命中 → PAC 验证可能成功
│   │   └── 缓存未命中 → PAC 验证失败
│   └── 5. 记录结果
└── 收集所有成功的 PAC 值

阶段三: 验证利用
├── 使用找到的正确 PAC 值
├── 构造有效的认证指针
├── 将指针用于目标操作
└── 实现控制流劫持
```

### 4.3 PACMAN 攻击复杂度分析

```
复杂度分析:
├── 时间复杂度
│   ├── 16 bit PAC: 65,536 次尝试
│   ├── 每次尝试需要:
│   │   ├── 内存写入: ~100ns
│   │   ├── 指针验证: ~100ns
│   │   ├── 缓存探测: ~1000ns
│   │   └── 总计: ~1200ns
│   ├── 16 bit PAC 总时间: ~78ms
│   ├── 20 bit PAC 总时间: ~1.25s
│   └── 24 bit PAC 总时间: ~20s
├── 空间复杂度
│   ├── 需要控制一个可写的指针位置
│   ├── 需要缓存侧信道缓冲区
│   └── 空间需求相对较小
└── 成功率
    ├── 理论成功率: 100%（遍历所有可能值）
    ├── 实际成功率: 受噪声影响，可能需要多次尝试
    └── 误报率: 可通过多次验证降低
```

## 5. XPAC 漏洞利用技术

### 5.1 XPAC 攻击原理

XPAC 攻击利用了 ARM64 指针地址的非规范形式（Non-Canonical Form）。在 ARM64 中，有效地址的高位必须是符号扩展的，但 PAC 计算时可能不检查这一点。

#### 5.1.1 非规范指针

```
指针规范形式:
├── 规范指针（Canonical）
│   ├── 高位是有效地址位的符号扩展
│   ├── 用户态: 高位全为 0
│   ├── 内核态: 高位全为 1
│   └── PAC 存储在高位中
├── 非规范指针（Non-Canonical）
│   ├── 高位不是正确的符号扩展
│   ├── 包含额外的信息
│   └── 可以被利用来携带伪造的 PAC
└── XPAC 利用
    ├── 构造非规范指针
    ├── 在高位嵌入伪造的 PAC
    ├── 利用 PAC 验证的漏洞
    └── 使非规范指针通过验证
```

#### 5.1.2 攻击机制

```
XPAC 攻击机制:
├── 步骤一: 指针获取
│   └── 获取受 PAC 保护的指针
├── 步骤二: PAC 剥离
│   └── 使用 XPACI 剥离原始 PAC
├── 步骤三: 地址修改
│   └── 修改指针的有效地址位
├── 步骤四: 伪造 PAC 嵌入
│   └── 在高位嵌入精心计算的伪造 PAC
├── 步骤五: 验证绕过
│   └── 利用验证逻辑的漏洞使伪造指针通过验证
└── 步骤六: 指针使用
    └── 使用伪造指针实现攻击目标
```

### 5.2 XPAC 在 DarkSword 中的应用

#### 5.2.1 内核对象伪造

```

```

├── 堆对象未初始化字段
│   ├── 新分配对象中的残留数据
│   ├── 可能包含前一个对象的 PAC 指针
│   └── 通过信息泄露漏洞读取
└── 内核缓冲区泄露
    ├── 拷贝到用户态时的未清理数据

├── 缓存侧信道
│   ├── PAC 验证影响缓存状态

## 13. 总结

### 13.1 主要发现

1. **PAC 显著提升了攻击门槛**: PAC 的引入使得传统的控制流劫持技术大幅失效
2. **PAC 并非不可绕过**: PACMAN、XPAC 等技术证明了 PAC 可以被绕过
3. **纵深防御至关重要**: 单一依赖 PAC 是不够的，需要多层防护
4. **信息泄露是关键**: 大多数 PAC 绕过都依赖于信息泄露作为前提
5. **侧信道是持续威胁**: 硬件侧信道为 PAC 绕过提供了可行路径

### 13.2 防御建议

1. 持续加强 PAC 实现的安全性
2. 结合多种安全机制构建纵深防御
3. 减少信息泄露的可能性
4. 加强侧信道防护
5. 推进内存安全语言的使用

### 13.3 研究展望

- 更长的 PAC 认证码
- 每进程独立的 PAC 密钥
- 与 MTE 的深度协同
- 硬件级的侧信道防护
- 形式化验证 PAC 实现
