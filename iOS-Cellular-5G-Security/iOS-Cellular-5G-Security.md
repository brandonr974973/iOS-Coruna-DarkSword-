### 1.3 iOS 的蜂窝安全哲学

Apple 对蜂窝安全采用多层防御：

1. **硬件隔离**：基带处理器独立于应用处理器
2. **加密优先**：所有蜂窝流量默认加密
3. **隐私保护**：SUPI/SUCI 隐藏用户身份
4. **安全启动**：基带固件签名验证
5. **持续更新**：定期修复基带漏洞

### 3.2 LTE 认证与密钥协商（EPS-AKA）

```
EPS-AKA 认证流程:

1. 附着请求
   UE → MME: Attach Request (IMSI 或 GUTI)
   
2. 认证请求
   MME → HSS: Authentication Info Request
   HSS: 生成 RAND, XRES, AUTN, KASME
   HSS → MME: Authentication Vector (AV)
   
3. 认证挑战
   MME → UE: Authentication Request (RAND, AUTN)
   
4. 认证响应
   UE: 验证 AUTN (使用 Ki)
   UE: 计算 RES
   UE → MME: Authentication Response (RES)
   
5. 认证验证
   MME: 比较 RES 和 XRES
   如果匹配: 认证成功
   
6. 密钥派生
   UE 和 MME 独立派生:
   - KASME (根密钥)
   - KNASenc (NAS 加密密钥)
   - KNASint (NAS 完整性密钥)
   - KeNB (基站密钥)
   - Kuplinkenc (上行加密)
   - Kdownlinkenc (下行加密)
```

### 3.3 LTE 加密算法

| 算法 | 密钥长度 | 用途 | 安全性 |
|------|---------|------|--------|
| EEA0 | - | 无加密 | ❌ 不安全 |
| EEA1 (SNOW 3G) | 128 bit | 用户面/控制面 | ✓ 安全 |
| EEA2 (AES-128) | 128 bit | 用户面/控制面 | ✓✓ 最安全 |
| EEA3 (ZUC) | 128 bit | 用户面/控制面 | ✓ 安全 |

### 3.4 LTE 完整性保护

| 算法 | 密钥长度 | 用途 | 安全性 |
|------|---------|------|--------|
| EIA0 | - | 无完整性 | ❌ 不安全 |
| EIA1 (SNOW 3G) | 128 bit | 控制面 | ✓ 安全 |
| EIA2 (AES-128) | 128 bit | 控制面 | ✓✓ 最安全 |
| EIA3 (ZUC) | 128 bit | 控制面 | ✓ 安全 |

**注意**：LTE 用户面无完整性保护，只有加密。

### 3.5 LTE 安全限制

```
LTE 安全限制:

1. IMSI 明文传输
   - 首次附着时 IMSI 明文发送
   - 可被 IMSI 捕获器截获
   - 用于追踪用户位置

2. 降级攻击
   - 攻击者可强制设备使用 2G
   - 2G 加密弱，易被破解
   - iOS 检测但无法完全阻止

3. SS7 攻击
   - 核心网信令协议漏洞
   - 可拦截通话、短信
   - 可追踪位置

4. 用户面无完整性
   - 只加密，无完整性保护
   - 可能被篡改（如果加密被破解）
```

## 5. 5G NSA 安全机制

### 5.1 NSA 架构安全

```
5G NSA (Option 3x) 安全:

┌─────────────────────────────────────────────────────────────────┐
│  UE (iOS 设备)                                                  │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │  4G LTE 连接 (锚点)                                      │ │
│  │  - 控制面: 4G LTE (eNodeB → MME → EPC)                  │ │
│  │  - 用户面: 4G + 5G 双连接                                │ │
│  └───────────────────────────────────────────────────────────┘ │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │  5G NR 连接 (辅助)                                       │ │
│  │  - 控制面: 无 (由 4G 管理)                               │ │
│  │  - 用户面: 5G gNB → EPC                                  │ │
│  └───────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘

安全特性:
  ✓ 5G 无线接口加密
  ✗ 控制面仍使用 4G 安全
  ✗ IMSI 仍可能明文传输
  ✗ 依赖 4G 核心网安全
```

### 5.2 NSA 安全限制

```
NSA 安全限制:

1. 控制面依赖 4G
   - 认证使用 EPS-AKA (4G)
   - 无法使用 5G-AKA
   - IMSI 可能明文传输

2. 核心网是 4G EPC
   - 无法使用 5G 安全增强
   - 无网络切片隔离
   - 无服务化架构安全

3. 移动性管理
   - 切换由 4G 控制
   - 可能降级到纯 4G
   - 安全风险与 4G 相同

结论: NSA 提供 5G 速度，但安全接近 4G
```

### 6.2 5G-AKA 认证

```
5G-AKA 认证流程:

1. 注册请求
   UE → AMF: Registration Request (SUCI 或 GUTI)
   
2. 认证请求
   AMF → UDM: Nudm_UEAuthentication_Get
   UDM: 从 SUCI 恢复 SUPI
   UDM → AUSF: 认证请求
   
3. 认证向量生成
   AUSF → UDM: 请求认证向量
   UDM: 使用 Ki 生成 AV (RAND, AUTN, XRES*, KAUSF)
   UDM → AUSF: 认证向量
   
4. 认证挑战
   AUSF → AMF: 认证数据
   AMF → UE: Authentication Request (RAND, AUTN)
   
5. 认证响应
   UE: 验证 AUTN
   UE: 计算 RES*
   UE → AMF: Authentication Response (RES*)
   
6. 认证验证
   AMF → AUSF: 验证请求 (RES*)
   AUSF: 比较 RES* 和 XRES*
   AUSF → AMF: 认证结果
   
7. 密钥派生
   KAUSF → KSEAF → KAMF → KNASenc, KNASint, KgNB
```

### 6.3 EAP-AKA' 认证

```
EAP-AKA' 认证:

用于:
  - 非 3GPP 接入 (Wi-Fi)
  - 漫游场景
  - 第三方认证

流程:
  1. UE 发起 EAP 认证
  2. 网络发送 EAP-Request/AKA'-Challenge
  3. UE 验证并响应
  4. 双方派生密钥

优势:
  ✓ 支持多种接入方式
  ✓ 灵活的认证方式
  ✓ 与 5G-AKA 互操作
```

## 7. 5G 用户隐私保护（SUPI/SUCI）

### 7.1 隐私问题背景

```
4G 隐私问题:

问题: IMSI 明文传输
  - 首次附着时发送 IMSI
  - IMSI 是永久标识符
  - 可被 IMSI 捕获器截获
  - 用于追踪用户位置和身份

攻击场景:
  1. 攻击者部署 IMSI 捕获器
  2. 捕获附近设备的 IMSI
  3. 追踪设备移动轨迹
  4. 关联用户身份
```

### 7.2 SUCI 解决方案

```
5G SUCI (Subscription Concealed Identifier):

概念:
  SUPI = 永久用户标识 (类似 IMSI)
  SUCI = SUPI 的加密版本
  
  SUCI = HomeNetworkPublicKeyID + EncryptedSUPI

格式:
  SUCI = 
    mcc-mnc (移动国家码-移动网络码)
    routing-indicator (路由指示)
    protection-scheme-id (保护方案 ID)
    home-network-public-key-id (公钥 ID)
    scheme-output (加密输出)

示例:
  SUPI: 460001234567890 (IMSI)
  SUCI: 460-00-0-1-0-abc123def456... (加密)
```

### 7.3 SUCI 加密方案

```
SUCI 加密方案:

方案 1: Profile A (ECIES)
  - 使用椭圆曲线加密
  - Curve25519 密钥交换
  - AES-128-CTR 加密
  - HMAC-SHA-256 完整性

方案 2: Profile B (ECIES)
  - 使用 secp256r1 曲线
  - AES-128-CTR 加密
  - HMAC-SHA-256 完整性

加密流程:
  1. UE 获取归属网络公钥
  2. 生成临时密钥对
  3. 使用网络公钥加密 SUPI
  4. 发送 SUCI 到网络
  5. 网络使用私钥解密恢复 SUPI

安全特性:
  ✓ SUPI 永不明文传输
  ✓ 防止 IMSI 捕获器
  ✓ 前向保密 (临时密钥)
  ✓ 防重放 (时间戳/计数器)
```

### 7.4 iOS 的 SUCI 实现

```swift
// SUCI 生成伪代码
func generateSUCI(supi: String, networkKey: PublicKey) -> String {
    // 1. 解析 SUPI
    let mcc = supi.prefix(3)  // 460
    let mnc = supi[3..<5]     // 00
    let msin = supi[5..<15]   // 1234567890
    
    // 2. 生成临时密钥对
    let ephemeralKey = generateEphemeralKeyPair()  // Curve25519
    
    // 3. 计算共享密钥
    let sharedSecret = ecdh(ephemeralKey.privateKey, networkKey.publicKey)
    
    // 4. 派生加密密钥
    let encryptionKey = kdf(sharedSecret, "encryption")
    let macKey = kdf(sharedSecret, "mac")
    
    // 5. 加密 MSIN
    let encryptedMSIN = aesCTR(encryptionKey, msin)
    
    // 6. 计算 MAC
    let mac = hmacSHA256(macKey, encryptedMSIN)
    
    // 7. 组装 SUCI
    let suci = "\(mcc)-\(mnc)-0-1-0-\(encryptedMSIN.base64)-\(mac.base64)"
    
    return suci
}
```

### 8.1 5G 加密算法套件

|------|---------|------|--------|

### 8.2 256 位加密优势

```
256 位加密 vs 128 位:

128 位:
  - 密钥空间: 2^128 ≈ 3.4 × 10^38
  - 当前安全: ✓ 足够
  - 量子威胁: ⚠️ Grover 算法降至 64 位

256 位:
  - 密钥空间: 2^256 ≈ 1.2 × 10^77
  - 当前安全: ✓✓ 非常安全
  - 量子威胁: ✓ Grover 算法降至 128 位 (仍安全)

结论: 256 位提供量子安全余量
```

### 8.3 iOS 的加密算法选择

```
iOS 5G 加密算法优先级:

1. 256-EA2 (AES-256) - 首选
2. 256-EA1 (SNOW 3G) - 次选
3. 128-EA2 (AES-128) - 兼容
4. 128-EA1 (SNOW 3G) - 兼容
5. 128-EA3 (ZUC) - 中国标准

协商流程:
  1. UE 发送支持的算法列表
  2. 网络选择最高优先级算法
  3. 双方使用协商的算法
```

```

算法:

参数 S 包含:

安全特性:
  ✓ 单向性 (无法逆推)
  ✓ 抗碰撞 (不同输入产生不同输出)
  ✓ 密钥分离 (不同用途产生不同密钥)
```
