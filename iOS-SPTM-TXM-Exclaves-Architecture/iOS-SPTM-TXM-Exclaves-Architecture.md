## 1. 引言：从单体内核到分区化安全

### 1.1 背景

Apple 的 iOS 安全架构长期以来建立在一个核心假设之上：XNU 内核作为系统的最高信任锚点，控制着所有硬件资源和敏感操作。然而，这一假设在近年来遭受了严峻挑战。随着内核漏洞利用技术的不断成熟——从早期的简单提权到如今的完整 exploit chain（如 DarkSword 套件展示的 WebKit RCE → 沙箱逃逸 → PAC 绕过 → 内核提权路径）——Apple 不得不重新审视其安全架构的根本设计。

iOS 18 标志着 Apple 安全哲学的一次根本性转变：从"内核即最高信任"的单极模型，转向"分区化信任"的多域模型。这一转变的核心是三个相互协作的安全组件：

- **SPTM（Secure Page Table Monitor）**：安全页表监控器，作为内存权限重类型的唯一权威
- **TXM（Trusted Execution Monitor）**：可信执行监控器，负责代码签名与权限验证
- **Exclaves**：安全世界隔离架构，将敏感服务移出 XNU 的直接控制范围

### 1.2 范式转移的意义

这一架构变革的意义在于：即使攻击者完全控制了 XNU 内核，也无法直接访问被 SPTM 域隔离的敏感资源。这从根本上改变了内核漏洞利用的价值——从"获得系统完全控制"降级为"获得部分系统控制，但敏感数据仍然不可达"。

正如 Steffin 和 Classen 在其研究中指出的，Apple 正在将"关键和敏感组件移出 XNU 的直接控制范围"，确保"内核妥协不再具有即时且重大的影响"。

### 1.3 分析范围

本报告从防御性安全视角出发，系统分析 SPTM、TXM 和 Exclaves 的设计原理、技术实现、协同机制及其对整体安全态势的影响。分析基于公开发表的研究论文、Apple 官方安全文档和独立安全研究者的技术发现。

## 2. XNU 内核的传统安全模型与局限

### 2.1 XNU 的混合内核架构

XNU（XNU's Not Unix）是 Apple 操作系统的核心内核，采用混合架构设计，融合了以下组件：

- **Mach 微内核**：提供基础的任务管理、虚拟内存和进程间通信原语
- **BSD 层**：提供 POSIX 兼容的系统调用、文件系统和网络栈
- **I/O Kit**：基于 C++ 的设备驱动程序框架
- **安全策略层**：包括 MACF（Mandatory Access Control Framework）和沙箱机制

### 2.2 单极信任模型

在传统 XNU 架构中，所有内核代码运行在同一个特权域内。尽管存在用户空间的沙箱隔离，但内核空间本身缺乏有效的内部隔离机制。这意味着：

1. **单一信任域**：所有内核代码和驱动程序共享同一个特权级别（EL1/EL2 in ARM 术语）
2. **无内部边界**：一个内核组件的漏洞可以被利用来影响任何其他内核组件
3. **全有或全无**：一旦攻击者获得内核执行权限，就可以访问系统上的所有数据和功能

### 2.3 传统安全机制

Apple 在 XNU 之上构建了多层安全机制来弥补这一架构缺陷：

#### 2.3.1 KTRR（Kernel Text Read-only Region）

KTRR 通过硬件机制将内核代码段标记为只读，防止运行时修改内核代码。然而，KTRR 仅保护代码段，对数据段和堆内存的攻击无能为力。

#### 2.3.2 PAC（Pointer Authentication Code）

PAC 通过 ARMv8.3 的指针认证机制，为函数指针和返回地址添加加密签名，防止控制流劫持。但 PAC 不保护数据完整性，且存在旁路攻击的可能。

#### 2.3.3 PPL（Page Protection Layer）

PPL 是 Apple 在 iOS 14 中引入的内存保护机制，通过一个独立的信任锚点来验证页表修改操作。PPL 是 SPTM 的前身，但其功能范围有限，且存在已知的绕过技术（如 Google Project Zero 在 2020 年披露的攻击方法）。

#### 2.3.4 沙箱与 TCC

用户空间的应用隔离通过沙箱配置文件（seatbelt profiles）和 TCC（Transparency, Consent, and Control）系统实现。这些机制在用户空间提供了有效的隔离，但它们的执行仍然依赖于内核的正确性。

### 2.4 根本局限

传统模型的根本局限在于：所有内核级安全机制的执行者本身就是被保护对象的一部分。这创造了一个循环依赖：

```
内核保护内核 → 如果内核被攻破，保护机制失效 → 所有依赖内核保护的机制同时失效
```

这一局限在以下场景中尤为突出：

- **内核漏洞利用**：攻击者获得内核执行权限后，可以禁用所有安全机制
- **物理内存访问**：直接修改物理页表可以绕过所有虚拟内存保护
- **侧信道攻击**：利用硬件侧信道可以提取内核中的加密密钥

## 3. Apple Silicon 硬件安全基础

### 3.1 ARM 异常级别模型

Apple Silicon 基于 ARM 架构，使用以下异常级别（Exception Levels）：

| 级别 | 名称 | 用途 |
|------|------|------|
| EL0 | User | 用户空间应用程序 |
| EL1 | Kernel | XNU 内核（传统内核模式） |
| EL2 | Hypervisor | 虚拟机监控器 / 安全监控 |
| EL3 | Secure Monitor | 安全世界切换（TrustZone） |

### 3.2 Apple 的扩展：Guarded Exception Levels

Apple 在标准 ARM 异常级别基础上引入了 **Guarded Exception Levels（GXL）**，创造了横向的隔离级别：

| GL 级别 | 名称 | 用途 |
|---------|------|------|
| GL0 | Guarded Level 0 | TXM 运行级别 |
| GL1 | Guarded Level 1 | 安全内核（SK）运行级别 |
| GL2 | Guarded Level 2 | SPTM 运行级别（最高特权） |

这些 GL 级别与传统的 EL 级别正交，提供了额外的隔离维度。即使代码运行在 EL1（内核模式），如果它不在正确的 GL 级别上，也无法访问受保护的资源。

### 3.3 硬件辅助的内存保护

Apple Silicon 提供了以下硬件安全特性：

1. **SPRR（Shadow Permission Remap Registers）**：影子权限重映射寄存器，允许原子地切换内存页的权限
2. **GXF（Guarded Execution Feature）**：守护执行特性，提供受保护的执行模式
3. **PAC（Pointer Authentication Code）**：指针认证码，保护控制流完整性
4. **MTE（Memory Tagging Extension）**：内存标签扩展，检测内存安全错误
5. **KTRR/KTRR_L2**：内核文本只读区域，保护内核代码完整性

## 4. SPRR：影子权限重映射寄存器

### 4.1 设计原理

SPRR（Shadow Permission Remap Registers）是 Apple Silicon 中的一项关键硬件安全特性，它重新定义了页表项中权限位的含义。

在传统 ARM 架构中，页表项直接编码页面的访问权限（读/写/执行）。SPRR 将这些权限位重新解释为**索引值**，指向一个寄存器表中的权限配置。

### 4.2 工作机制

```
传统模型：
  页表项权限位 → 直接决定页面权限（R/W/X）

SPRR 模型：
  页表项权限位 → 索引值 → SPRR 寄存器表 → 实际权限配置
```

这一设计的关键优势在于：

1. **原子权限切换**：通过修改 SPRR 寄存器表，可以原子地改变所有使用特定索引的页面的权限
2. **细粒度控制**：不同的执行模式可以使用不同的权限映射
3. **快速上下文切换**：权限切换不需要遍历和修改页表项

### 4.3 与 GXF 的协同

SPRR 与 GXF 协同工作，为不同的 Guarded Level 提供不同的内存权限视图：

- 当 CPU 运行在 GL0 时，SPRR 使用 GL0 的权限映射
- 当 CPU 运行在 GL1 时，SPRR 使用 GL1 的权限映射
- 当 CPU 运行在 GL2 时，SPRR 使用 GL2 的权限映射

这意味着同一段物理内存，在不同的 GL 级别下可以有不同的访问权限。例如，SPTM 的代码在 GL2 下可执行，但在 GL0 或 GL1 下完全不可访问。

### 4.4 安全意义

SPRR 为 SPTM 的安全模型提供了硬件基础：

- **内存重类型化**：SPTM 可以通过修改 SPRR 配置来改变内存页的"类型"（权限组合）
- **域隔离**：不同的 SPTM 域使用不同的 SPRR 索引，确保域间内存不可互访
- **原子性保证**：权限切换是硬件原子的，不存在竞态条件窗口

## 5. GXF：守护执行特性

### 5.1 概述

GXF（Guarded Execution Feature）是 Apple Silicon 中实现 Guarded Exception Levels 的硬件机制。它提供了一套受保护的执行模式，允许在不同信任级别之间安全切换。

### 5.2 GENTER 指令

GXF 的核心是 **GENTER** 指令（编码 `0x00201420`），用于从低信任级别进入高信任级别：

```
正常执行流（GL0/GL1） → GENTER → 守护执行模式（GL2）
```

GENTER 的执行过程：

1. 保存当前执行上下文（PC、SP、寄存器状态）
2. 切换 SPRR 权限映射到目标 GL 级别
3. 跳转到预注册的守护入口点
4. 开始在高信任级别执行

### 5.3 GEXIT 指令

**GEXIT** 指令用于从守护执行模式返回到正常执行模式：

```
守护执行模式（GL2） → GEXIT → 正常执行流（GL0/GL1）
```

GEXIT 的执行过程：

1. 验证返回目标的合法性
2. 恢复执行上下文
3. 切换 SPRR 权限映射回原始 GL 级别
4. 返回到调用点

### 5.4 安全约束

GXF 提供了以下安全约束：

1. **单向进入**：只能通过 GENTER 进入高 GL 级别，不能通过普通分支指令进入
2. **受控退出**：只能通过 GEXIT 或异常退出高 GL 级别
3. **上下文隔离**：不同 GL 级别的执行上下文完全隔离
4. **权限切换**：GL 级别切换自动触发 SPRR 权限映射切换

### 5.5 与 SPTM 的关系

SPTM 运行在 GL2，这是最高的 Guarded Level。XNU 内核通过 GENTER 指令进入 GL2 来调用 SPTM 的服务。一旦进入 GL2，SPTM 代码可以访问 XNU 无法访问的内存区域（如页表本身）。

```
XNU (EL1, GL0) → GENTER → SPTM (EL1, GL2) → GEXIT → XNU (EL1, GL0)
```

注意：GL 级别与 EL 级别是正交的。SPTM 运行在 EL1（内核模式）但 GL2（最高守护级别），这意味着它在传统的内核特权级别上运行，但拥有超越普通内核代码的内存访问权限。

## 6. PPL：页表保护层的遗产

### 6.1 PPL 的设计目标

PPL（Page Protection Layer）是 Apple 在 iOS 14 中引入的内存保护机制，旨在防止被攻破的内核随意修改关键页表项。PPL 的核心思想是：将页表修改的权限从内核中剥离，交给一个独立的、更小的信任锚点来执行。

### 6.2 PPL 的工作机制

PPL 的实现基于以下原则：

1. **页表本身受保护**：关键页表（如内核页表）被标记为只有 PPL 代码可以修改
2. **受控接口**：内核通过一组受限制的调用来请求 PPL 执行页表修改
3. **验证逻辑**：PPL 在執行修改前验证请求的合法性

### 6.3 PPL 的局限

Google Project Zero 在 2020 年发表的研究揭示了 PPL 的多个局限：

1. **攻击面仍然存在**：PPL 代码本身可能存在漏洞
2. **验证不完整**：PPL 的验证逻辑可能不够严格
3. **功能范围有限**：PPL 仅保护页表修改，不涵盖其他敏感操作
4. **单域模型**：PPL 仍然是一个单一的保护层，缺乏细粒度的域隔离

### 6.4 从 PPL 到 SPTM 的演进

SPTM 可以被视为 PPL 的继承者和扩展者。相比 PPL，SPTM 提供了：

| 特性 | PPL | SPTM |
|------|-----|------|
| 保护范围 | 仅页表修改 | 所有内存重类型化操作 |
| 隔离模型 | 单一保护层 | 多域隔离 |
| 硬件支持 | 部分 | 完整 SPRR/GXF |
| 信任域 | 单一 | 多个（SPTM 域） |
| 与内核关系 | 独立保护层 | 内核功能的重新分配 |

## 7. SPTM：安全页表监控器

### 7.1 概述

SPTM（Secure Page Table Monitor）是 Apple 在 iOS 16 / macOS 12 中引入的核心安全组件，作为系统中**内存重类型化的唯一权威**。SPTM 取代了 PPL 的角色，并将其功能大幅扩展。

### 7.2 运行环境

SPTM 运行在 **Guarded Level 2（GL2）**，这是 Apple Silicon 中最高的守护执行级别。这一特权级别确保：

- SPTM 的代码和数据在 GL0 和 GL1 下完全不可见、不可访问
- 只有 SPTM 自身可以修改其管理的内存区域
- 页表修改操作只能由 SPTM 执行

### 7.3 核心职责

SPTM 承担以下核心职责：

1. **内存重类型化**：所有内存页的权限变更必须经过 SPTM 验证和执行
2. **页表监控**：SPTM 监控所有页表修改操作，防止未授权的页表篡改
3. **域管理**：SPTM 管理多个信任域，控制域间的内存隔离
4. **SPRR 配置**：SPTM 管理 SPRR 寄存器表的配置，控制不同 GL 级别的权限映射

### 7.4 进入机制

XNU 内核通过以下方式调用 SPTM：

```
XNU 代码 (GL0) → 准备参数 → GENTER 指令 → SPTM 入口 (GL2) → 执行操作 → GEXIT → XNU (GL0)
```

GENTER 指令触发以下硬件行为：

1. 保存 GL0 的执行上下文
2. 切换到 GL2 的 SPRR 权限映射
3. 跳转到 SPTM 的受注册入口点
4. 开始在 GL2 下执行 SPTM 代码

### 7.5 安全检查流程

当 XNU 请求内存重类型化时，SPTM 执行以下验证：

1. **物理地址验证**：确认目标物理地址的合法性
2. **类型验证**：确认请求的新类型（权限组合）是否合法
3. **调用者权限验证**：确认调用者是否有权执行请求的操作
4. **域验证**：确认操作不会违反域隔离规则
5. **执行重类型化**：通过修改 SPRR 配置来原子地改变页面权限

### 7.6 与 PPL 的关键区别

SPTM 与 PPL 的关键区别在于其**域隔离能力**。PPL 是一个单一的保护层，而 SPTM 管理多个独立的信任域。每个域有自己的内存空间，域间的内存映射受到严格限制。

## 8. SPTM 的内存重类型化机制

### 8.1 内存类型系统

SPTM 引入了一个形式化的**内存类型系统**，每个物理页帧都有一个关联的"类型"，定义其访问权限和使用方式。

主要的内存类型包括：

| 类型 | 含义 | 典型用途 |
|------|------|----------|
| RW | 可读可写 | 普通数据页 |
| RO | 只读 | 代码页、常量数据 |
| RW-data | 数据页（可重映射） | 堆内存 |
| Page-table | 页表页 | 页表结构 |
| Guarded | 守护页 | SPTM/TXM 专属内存 |
| Free | 空闲页 | 未分配的页帧 |

### 8.2 重类型化操作

内存重类型化是指改变一个物理页帧的类型（从而改变其访问权限）的操作。在 SPTM 模型下，所有重类型化操作必须经过以下流程：

```
调用者请求 → SPTM 验证 → SPRR 更新 → 权限生效
```

具体步骤：

1. **请求提交**：XNU 或其他组件通过 GENTER 调用 SPTM，提交重类型化请求
2. **参数验证**：SPTM 验证请求参数的合法性
   - 物理地址是否有效
   - 新类型是否是合法的转换
   - 调用者是否有权执行此操作
3. **状态更新**：SPTM 更新内部的页帧类型记录
4. **SPRR 配置**：SPTM 更新 SPRR 寄存器表，使新权限生效
5. **返回结果**：SPTM 通过 GEXIT 返回操作结果

### 8.3 类型转换规则

SPTM 强制执行严格的类型转换规则。并非所有类型之间的转换都是允许的。例如：

- Free → RW：允许（分配空闲页）
- RW → RO：允许（代码段保护）
- RO → RW：需要验证（可能需要重新签名）
- RW → Page-table：允许（用于页表分配）
- Page-table → RW：需要验证（页表释放）
- Guarded → 任何非 Guarded 类型：禁止（除非通过特定释放流程）

### 8.4 安全保证

SPTM 的内存重类型化机制提供以下安全保证：

1. **唯一权威**：只有 SPTM（运行在 GL2）可以执行内存重类型化
2. **原子性**：权限变更通过 SPRR 原子生效，不存在中间状态
3. **可审计性**：所有重类型化操作都经过 SPTM 的验证逻辑
4. **域隔离**：重类型化操作不能跨越 SPTM 域边界

## 9. SPTM 域：信任域隔离

### 9.1 域的概念

SPTM 引入了**SPTM 域**的概念，将系统内存空间划分为多个独立的信任域。每个域有自己的：

- 内存空间（一组物理页帧）
- 权限策略（域内内存的访问规则）
- 执行环境（域专属的代码和数据）

### 9.2 域间隔离

SPTM 域之间的隔离通过以下机制实现：

1. **SPRR 隔离**：不同域使用不同的 SPRR 索引，确保域内内存只在对应域的执行环境中可见
2. **页表隔离**：每个域有独立的页表视图，不能直接映射其他域的内存
3. **受控交互**：域间的交互只能通过 SPTM 定义的受控接口进行

### 9.3 主要域

系统中存在以下主要 SPTM 域：

| 域 | 运行级别 | 功能 |
|----|----------|------|
| XNU 域 | GL0 | 传统内核功能 |
| TXM 域 | GL0（TXM 代码） | 代码签名与权限验证 |
| SK 域 | GL1 | Exclaves 安全内核 |
| SPTM 域 | GL2 | SPTM 自身（最高信任） |

### 9.4 域的生命周期

SPTM 域的生命周期由 SPTM 管理：

1. **创建**：在启动过程中，SPTM 创建各个域并分配初始内存
2. **配置**：SPTM 为每个域配置 SPRR 权限和页表映射
3. **运行**：域在配置的权限范围内独立运行
4. **交互**：域间通过受控接口进行必要的交互
5. **终止**：域可以被安全终止，其内存被回收

### 9.5 安全意义

SPTM 域隔离的安全意义在于：

- **爆炸半径缩减**：即使 XNU 域被完全攻破，攻击者也无法直接访问 TXM 域或 SK 域
- **横向移动困难**：攻击者需要分别攻破每个域才能实现横向移动
- **最小权限**：每个域只拥有其功能所需的最小权限

## 10. TXM：可信执行监控器

### 10.1 概述

TXM（Trusted Execution Monitor）是 Apple 安全架构中负责**代码签名和权限验证**的核心组件。TXM 从 XNU 内核中接管了代码签名验证的职责，确保代码完整性检查不受内核妥协的影响。

### 10.2 设计动机

在传统模型中，代码签名验证由 XNU 内核自身执行。这存在一个根本问题：如果内核被攻破，攻击者可以绕过代码签名检查，执行未签名的代码。

TXM 通过将代码签名验证移出 XNU 的控制范围来解决这一问题：

- TXM 运行在独立的 SPTM 域中
- XNU 通过受限制接口调用 TXM
- TXM 的代码和数据在 XNU 域中不可访问

### 10.3 运行环境

TXM 运行在 **GL0** 级别，但其代码和数据位于独立的 SPTM 域中。这意味着：

- TXM 代码在传统的内核特权级别（EL1）上运行
- 但 TXM 的内存空间与 XNU 的内存空间隔离
- XNU 无法直接读取或修改 TXM 的代码和数据

### 10.4 核心职责

TXM 承担以下核心职责：

1. **代码签名验证**：验证所有可执行代码的数字签名
2. **权限（Entitlement）验证**：验证进程的权限声明
3. **系统完整性检查**：验证系统组件的完整性
4. **签名状态管理**：维护代码签名状态的权威记录

### 10.5 与 XNU 的交互

XNU 通过以下方式与 TXM 交互：

```
XNU 需要验证代码签名 → 准备验证请求 → 调用 TXM 接口 → TXM 执行验证 → 返回结果
```

这一交互受到以下约束：

- XNU 只能通过 SPTM 定义的受控接口调用 TXM
- 调用参数受到严格验证
- TXM 的响应经过签名，防止篡改

## 11. TXM 的代码签名与权限验证

### 11.1 代码签名验证流程

TXM 的代码签名验证流程包括以下步骤：

1. **哈希计算**：计算可执行代码的加密哈希
2. **签名验证**：使用 Apple 的公钥验证代码签名
3. **证书链验证**：验证签名证书链的有效性
4. **权限提取**：从签名中提取权限（Entitlements）信息
5. **状态记录**：将验证结果记录到签名状态表中

### 11.2 权限（Entitlements）系统

Apple 的权限系统是一种细粒度的能力机制，定义进程可以执行的特权操作。TXM 负责：

- **验证权限声明**：确认进程的权限声明与其签名匹配
- **强制执行权限检查**：在进程请求特权操作时验证其权限
- **维护权限数据库**：保存所有已验证进程的权限信息

### 11.3 系统完整性验证

TXM 还负责验证系统组件的完整性：

- **内核扩展验证**：验证所有加载的内核扩展（kext）的签名
- **系统二进制验证**：验证系统关键二进制的完整性
- **启动链验证**：参与安全启动链的完整性验证

### 11.4 防篡改机制

TXM 的验证结果受到以下防篡改机制保护：

1. **签名状态表**：位于 TXM 域内，XNU 无法直接修改
2. **结果签名**：TXM 的验证结果经过加密签名
3. **独立存储**：签名状态存储在 TXM 专属内存中

## 12. TXM 与 SPTM 的协作模型

### 12.1 协作架构

TXM 和 SPTM 通过以下架构协作：

```
┌─────────────────────────────────────────┐
│              SPTM (GL2)                 │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐ │
│  │ XNU 域  │  │ TXM 域  │  │ SK 域   │ │
│  │ (GL0)   │  │ (GL0)   │  │ (GL1)   │ │
│  │         │  │ ┌─────┐ │  │         │ │
│  │  XNU    │──│→│ TXM │ │  │   SK    │ │
│  │         │  │ └─────┘ │  │         │ │
│  └─────────┘  └─────────┘  └─────────┘ │
│         ↑                              │
│    SVC 调用                             │
└─────────────────────────────────────────┘
```

### 12.2 TXM 调用 SPTM

TXM 需要 SPTM 的服务来管理其安全内存区域：

- TXM 通过 **Supervisor Calls（SVCs）** 调用 SPTM
- SPTM 验证 TXM 的请求并执行相应的内存操作
- 这些操作包括分配安全内存、修改权限等

### 12.3 XNU 调用 TXM

XNU 需要 TXM 的服务来验证代码签名：

- XNU 通过受限制接口调用 TXM
- 调用参数受到 SPTM 的监控和验证
- TXM 的响应经过签名，确保完整性

### 12.4 信任链

SPTM-TXM 协作建立了以下信任链：

1. **硬件信任根**：Apple Silicon 的 SPRR/GXF 提供硬件级隔离
2. **SPTM 信任锚**：SPTM 作为内存操作的唯一权威
3. **TXM 信任锚**：TXM 作为代码签名的权威验证者
4. **系统信任**：整个系统的完整性建立在这两个信任锚之上

## 13. Exclaves：安全世界隔离架构

### 13.1 概述

Exclaves 是 Apple 安全架构中最具创新性的组件之一。它将敏感的系统服务和资源隔离到称为 **Conclaves** 的独立执行环境中，从根本上减少了 XNU 内核可以直接访问的敏感数据量。

### 13.2 设计理念

Exclaves 的设计理念基于以下原则：

1. **最小暴露**：敏感服务不应该在内核空间中运行
2. **隔离执行**：敏感操作应该在独立的、受保护的环境中执行
3. **受控通信**：内核与敏感服务之间的通信必须经过严格的验证和过滤
4. **纵深防御**：即使内核被攻破，敏感数据仍然不可达

### 13.3 与传统模型的对比

| 方面 | 传统模型 | Exclaves 模型 |
|------|----------|---------------|
| 敏感服务位置 | 内核空间或内核可访问的内存 | 独立的 Conclave 环境 |
| 内核访问能力 | 内核可以直接访问所有敏感数据 | 内核无法直接访问 Conclave 内存 |
| 通信方式 | 直接函数调用或共享内存 | 通过 xnuproxy 和 Tightbeam IPC |
| 内核妥协影响 | 所有敏感数据暴露 | Conclave 内的数据仍然安全 |

### 13.4 保护的敏感服务

Exclaves 保护的敏感服务包括（但不限于）：

- **生物识别数据处理**：Face ID / Touch ID 的原始生物特征数据
- **音频处理**：受保护的音频流（如 Siri 语音数据）
- **传感器数据**：受保护的传感器数据访问
- **加密密钥操作**：某些加密密钥的使用和管理
- **安全存储**：受保护的数据存储区域

### 13.5 架构层次

Exclaves 的架构分为以下层次：

```
┌──────────────────────────────────────┐
│           用户空间应用                 │
│    (corespeechd, biometricd, etc.)   │
├──────────────────────────────────────┤
│         Tightbeam IPC 框架            │
├──────────────────────────────────────┤
│           xnuproxy                   │
│      (安全世界请求处理器)              │
├──────────────────────────────────────┤
│         安全内核 (SK)                 │
│          (GL1 微内核)                 │
├──────────────────────────────────────┤
│          Conclaves                   │
│    (隔离的执行容器)                    │
├──────────────────────────────────────┤
│           SPTM (GL2)                 │
│      (内存域隔离执行)                  │
└──────────────────────────────────────┘
```

## 14. Conclave：隔离执行容器

### 14.1 Conclave 的概念

**Conclave** 是 Exclaves 架构中的基本隔离单元。每个 Conclave 是一个独立的执行环境，拥有：

- 独立的代码空间（经过签名验证）
- 独立的数据空间（对其他域不可见）
- 独立的执行上下文
- 受控的外部通信接口

### 14.2 Conclave 的类型

系统中存在多种 Conclave，每种负责不同的敏感功能：

| Conclave 类型 | 功能 | 保护的资源 |
|---------------|------|------------|
| Audio Conclave | 音频处理 | 受保护的音频流 |
| Biometric Conclave | 生物识别处理 | 原始生物特征数据 |
| Sensor Conclave | 传感器数据处理 | 受保护的传感器数据 |
| Crypto Conclave | 加密操作 | 加密密钥和操作 |

### 14.3 Conclave 的隔离机制

Conclave 的隔离通过以下机制实现：

1. **SPTM 域隔离**：每个 Conclave 位于独立的 SPTM 域中
2. **SPRR 权限隔离**：Conclave 内存使用专属的 SPRR 索引
3. **页表隔离**：Conclave 有独立的页表视图
4. **执行隔离**：Conclave 代码在受保护的执行环境中运行

### 14.4 实验验证

Steffin 和 Classen 在其研究中进行了实际实验来验证 Conclave 的隔离效果：

- 他们向 `corespeechd`（语音处理守护进程）注入代码
- 注入的代码可以查询传感器状态（表明基本的系统交互仍然可能）
- 但当尝试复制音频数据时，**返回的是空字节（null bytes）**
- 这证明 Conclave 确实阻止了敏感数据从隔离环境中外泄

这一实验结果具有重要意义：它表明即使攻击者能够在与 Conclave 交互的进程中执行代码，也无法提取 Conclave 保护的敏感数据。

## 15. xnuproxy 与 Tightbeam IPC

### 15.1 xnuproxy：安全世界请求处理器

**xnuproxy** 是 Exclaves 架构中的关键组件，充当安全世界（Conclave 环境）与正常世界（XNU 内核及用户空间）之间的请求处理器。

xnuproxy 的职责包括：

1. **请求转发**：将来自用户空间的请求安全地转发到 Conclave
2. **参数验证**：验证请求参数的合法性，防止恶意输入
3. **结果过滤**：过滤从 Conclave 返回的结果，确保不泄露敏感数据
4. **身份验证**：验证请求者的身份和权限

### 15.2 Tightbeam IPC 框架

**Tightbeam** 是 Apple 专有的 IPC（进程间通信）框架，用于 Conclave 与客户端之间的消息传递。

Tightbeam 的设计特点：

1. **类型安全**：消息格式在编译时定义，运行时验证
2. **能力基础**：通信需要持有对应的能力（capability）
3. **零拷贝**：在可能的情况下使用零拷贝传输，提高性能
4. **审计日志**：所有 IPC 调用都可以被审计和追踪

### 15.3 通信流程

典型的 Conclave 通信流程如下：

```
用户空间客户端 → Tightbeam IPC → xnuproxy → 安全内核(SK) → Conclave
                                                              │
Conclave → 安全内核(SK) → xnuproxy → Tightbeam IPC → 用户空间客户端
```

### 15.4 安全约束

xnuproxy 和 Tightbeam 的通信受到以下安全约束：

- **消息大小限制**：防止缓冲区溢出和拒绝服务
- **消息类型验证**：只允许预定义的消息类型
- **频率限制**：防止高频调用导致的资源耗尽
- **权限检查**：验证调用者是否有权执行请求的操作

## 16. 安全内核 SK：Exclaves 的微内核

### 16.1 概述

**安全内核（Secure Kernel, SK）** 是 Exclaves 架构中的微内核组件，运行在 **GL1** 级别。SK 负责管理 Conclave 的生命周期和调度。

### 16.2 设计原则

SK 遵循微内核设计原则：

1. **最小功能集**：SK 只包含管理 Conclave 所需的最少功能
2. **最小代码量**：减少攻击面
3. **形式化验证**：SK 的关键组件可能经过形式化验证
4. **高可靠性**：作为安全关键组件，SK 需要极高的可靠性

### 16.3 核心功能

SK 的核心功能包括：

1. **Conclave 管理**：创建、销毁和调度 Conclave
2. **内存管理**：为 Conclave 分配和管理内存
3. **IPC 路由**：路由 Conclave 与外部之间的 IPC 消息
4. **SPTM 交互**：代表 Conclave 与 SPTM 交互，请求内存操作

### 16.4 运行环境

SK 运行在 GL1，这意味着：

- SK 的代码在 SPTM 域中受到保护
- XNU 无法直接访问 SK 的内存
- SK 可以通过 SPTM 的服务管理其内存域
- SK 的权限低于 SPTM（GL2）但高于 XNU（GL0）

## 17. SPTM-TXM-Exclaves 三层协同架构

### 17.1 整体架构

SPTM、TXM 和 Exclaves 共同构成了 Apple 的三层安全架构：

```
┌─────────────────────────────────────────────────────┐
│                    第三层：Exclaves                   │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │Conclave │ │Conclave │ │Conclave │ │Conclave │   │
│  │ (Audio) │ │(Biometric│ │(Sensor) │ │(Crypto) │   │
│  └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘   │
│       └───────────┴───────────┴───────────┘         │
│                        │                             │
│              ┌─────────┴─────────┐                   │
│              │   安全内核 (SK)    │ ← GL1            │
│              └─────────┬─────────┘                   │
│                        │                             │
│              ┌─────────┴─────────┐                   │
│              │  xnuproxy/TB IPC  │                   │
│              └─────────┬─────────┘                   │
├────────────────────────┼────────────────────────────┤
│                    第二层：TXM                        │
│              ┌─────────┴─────────┐                   │
│              │  代码签名验证       │ ← GL0 (TXM 域)   │
│              │  权限验证          │                   │
│              │  完整性检查        │                   │
│              └─────────┬─────────┘                   │
├────────────────────────┼────────────────────────────┤
│                    第一层：SPTM                       │
│              ┌─────────┴─────────┐                   │
│              │  内存重类型化       │ ← GL2 (最高信任)  │
│              │  域管理            │                   │
│              │  SPRR 配置         │                   │
│              │  页表监控          │                   │
│              └─────────┬─────────┘                   │
├────────────────────────┼────────────────────────────┤
│                    XNU 内核                          │
│              ┌─────────┴─────────┐                   │
│              │  传统内核功能       │ ← GL0 (XNU 域)   │
│              │  设备驱动          │                   │
│              │  网络栈            │                   │
│              └───────────────────┘                   │
└─────────────────────────────────────────────────────┘
```

### 17.2 信任关系

三层之间的信任关系如下：

1. **SPTM 信任所有下层组件**：SPTM 作为最高信任锚，管理所有域的内存
2. **TXM 信任 SPTM**：TXM 依赖 SPTM 来保护其内存域
3. **Exclaves 信任 SPTM 和 TXM**：Conclave 依赖 SPTM 进行内存隔离，依赖 TXM 进行代码验证
4. **XNU 不直接信任任何上层组件**：XNU 通过受控接口与上层交互

### 17.3 数据流

典型的数据流（以生物识别验证为例）：

```
1. 用户空间应用请求生物识别验证
2. 请求通过 Tightbeam IPC 发送到 xnuproxy
3. xnuproxy 验证请求合法性
4. 请求转发到安全内核 (SK)
5. SK 调度到 Biometric Conclave
6. Conclave 执行生物识别匹配（原始数据不出 Conclave）
7. Conclave 返回匹配结果（仅返回 yes/no，不返回原始数据）
8. 结果通过 SK → xnuproxy → Tightbeam 返回给用户空间
```

在整个流程中：

- XNU 内核不参与数据处理
- 原始生物特征数据始终在 Conclave 内
- 只有验证结果（是/否）被返回

## 18. 攻击面缩减分析

### 18.1 传统模型的攻击面

在传统 XNU 模型中，内核漏洞利用的攻击面包括：

- 所有内核数据结构
- 所有加密密钥（存储在 kernel memory 中）
- 所有用户数据（内核可以访问所有进程内存）
- 所有安全机制（可以被禁用以维持持久化）

### 18.2 新模型的攻击面缩减

在 SPTM-TXM-Exclaves 模型中，即使 XNU 被完全攻破，攻击者的攻击面显著缩减：

| 资源 | 传统模型 | 新模型 |
|------|----------|--------|
| 加密密钥 | 可访问 | 部分不可达（Conclave 保护的密钥） |
| 生物特征数据 | 可访问 | 不可达（在 Conclave 内） |
| 音频数据 | 可访问 | 不可达（在 Conclave 内） |
| 代码签名绕过 | 可能（修改内核验证逻辑） | 困难（TXM 独立验证） |
| 持久化机制 | 可修改内核组件 | 受限（受保护组件不可修改） |

### 18.3 攻击者需要突破的层次

在新模型下，攻击者要实现完整的系统控制，需要突破以下层次：

```
第一层：用户空间沙箱逃逸 → 获得内核执行权限
第二层：XNU 内核漏洞利用 → 获得 XNU 域控制
第三层：SPTM 域隔离绕过 → 访问 TXM/SK 域（需要 SPTM 漏洞）
第四层：Conclave 隔离绕过 → 访问敏感数据（需要 Conclave 漏洞）
```

每一层都需要独立的漏洞利用技术，且层间存在硬件隔离（SPRR/GXF），大大增加了攻击的复杂度和成本。

### 18.4 对内核漏洞价值的影响

新模型从根本上影响了内核漏洞的价值：

- **传统价值**：内核漏洞 = 系统完全控制
- **新价值**：内核漏洞 = 部分系统控制（敏感数据仍然安全）

这一变化对于以下场景尤为重要：

- **间谍软件攻击**：即使获得内核权限，也无法窃取生物特征数据
- **物理取证**：即使通过物理手段获取内核内存，部分数据仍然加密隔离
- **持久化攻击**：即使建立持久化，也无法访问 Conclave 保护的资源

## 19. 对现有漏洞利用链的影响

### 19.1 对 DarkSword 攻击链的影响

DarkSword 攻击链（CVE-2025-14174 → CVE-2026-20700 → CVE-2025-43510 → CVE-2025-43520）代表了当前最先进的 iOS 漏洞利用技术。在新架构下：

- **WebKit RCE（CVE-2025-14174）**：仍然有效，但只获得沙箱内的执行权限
- **沙箱逃逸**：仍然可能，但获得的是 XNU 域的控制权
- **PAC 绕过（CVE-2026-20700）**：允许在内核中执行代码，但受限于 XNU 域
- **内核提权（CVE-2025-43510/43520）**：获得 XNU 内核的完全控制，但无法访问 Conclave 数据

这意味着 DarkSword 攻击链在新架构下的效果被显著削弱：攻击者获得了内核权限，但无法访问最有价值的敏感数据。

### 19.2 对 Pegasus/Triangulation 类攻击的影响

Pegasus 和 Operation Triangulation 等间谍软件依赖内核权限来窃取敏感数据。在新架构下：

- **通信拦截**：部分通信数据可能仍然可访问（如果在 XNU 域中处理）
- **位置数据**：GPS 数据可能在 XNU 域中可访问
- **生物特征数据**：不可达（在 Conclave 内）
- **加密密钥**：部分不可达（Conclave 保护的密钥）
- **音频/视频**：不可达（在 Conclave 内处理）

### 19.3 对越狱的影响

传统越狱需要获得内核权限并修改系统行为。在新架构下：

- **内核越狱**：仍然可能获得 XNU 域的控制
- **系统修改**：受限于 XNU 域，无法修改受保护的组件
- **持久化**：受保护区域的持久化需要突破 SPTM 域隔离
- **完全越狱**：需要额外的 SPTM/TXM 漏洞才能实现完全控制

### 19.4 攻击者的适应策略

面对新架构，攻击者可能需要：

1. **寻找 SPTM 漏洞**：直接攻击 SPTM 以突破域隔离
2. **寻找 Conclave 漏洞**：攻击 Conclave 内部的服务
3. **寻找 xnuproxy 漏洞**：攻击 IPC 层以操纵 Conclave 通信
4. **侧信道攻击**：通过侧信道从 Conclave 提取信息
5. **供应链攻击**：在 Conclave 代码签名前植入恶意代码

## 20. 与 Secure Enclave 的关系与区别

### 20.1 Secure Enclave 概述

Secure Enclave 是 Apple 独立的硬件安全协处理器，拥有独立的：

- 处理器核心（ARM Cortex 系列）
- 安全启动链
- 加密引擎
- 安全存储（SEP OS）

### 20.2 SPTM/TXM/Exclaves 与 Secure Enclave 的关系

SPTM/TXM/Exclaves 与 Secure Enclave 是互补的安全机制：

| 方面 | Secure Enclave | SPTM/TXM/Exclaves |
|------|----------------|-------------------|
| 实现方式 | 独立硬件协处理器 | 主处理器上的软件+硬件隔离 |
| 运行位置 | 独立的 SEP 芯片/模块 | 主 Apple Silicon 芯片 |
| 主要功能 | 密钥管理、生物特征匹配、安全启动 | 内存保护、代码验证、服务隔离 |
| 隔离级别 | 物理隔离 | 逻辑隔离（硬件辅助） |
| 性能影响 | 需要跨芯片通信 | 同芯片，性能开销较小 |

### 20.3 协同工作

两者协同工作提供全面的安全保护：

1. **安全启动**：Secure Enclave 验证启动链 → SPTM 保护运行时内存
2. **密钥管理**：Secure Enclave 存储密钥 → Exclaves 使用密钥进行加密操作
3. **生物识别**：Secure Enclave 执行匹配 → 结果通过安全通道返回 Conclave
4. **数据保护**：Secure Enclave 提供加密引擎 → SPTM 保护加密数据的内存

### 20.4 安全层次

```
最高安全层：Secure Enclave（物理隔离）
    ↓
第二层：SPTM (GL2)（硬件辅助逻辑隔离）
    ↓
第三层：TXM (GL0, 独立域)（代码完整性）
    ↓
第四层：Exclaves/SK (GL1)（服务隔离）
    ↓
第五层：XNU 内核 (GL0)（传统内核安全）
    ↓
最低层：用户空间（沙箱隔离）
```

## 21. 安全研究方法论

### 21.1 研究挑战

研究 Apple 的安全架构面临以下挑战：

1. **闭源实现**：SPTM/TXM/Exclaves 的实现代码不公开
2. **硬件依赖**：SPRR/GXF 是 Apple Silicon 专有特性
3. **文档有限**：Apple 官方文档对这些组件的描述非常有限
4. **设备要求**：需要较新的 Apple Silicon 设备进行研究

### 21.2 研究方法

安全研究者使用以下方法来研究这些组件：

1. **固件分析**：从 iOS 固件镜像中提取和分析相关代码
2. **动态调试**：使用硬件调试器观察运行时行为
3. **侧信道分析**：通过时序、功耗等侧信道推断内部机制
4. **漏洞研究**：通过寻找漏洞来理解安全边界
5. **形式化分析**：对安全属性进行形式化验证

### 21.3 研究发现

目前已公开的主要研究发现包括：

- Steffin & Classen (2025)：首次全面描述 SPTM/TXM/Exclaves 架构
- Sven Peter (2021)：SPRR 和 GXF 的逆向工程分析
- Google Project Zero (2020)：PPL 的安全分析和绕过技术
- 多个安全会议演讲：关于 Apple Silicon 安全特性的研究

## 22. 防御策略与建议

### 22.1 对开发者的建议

1. **利用系统安全特性**：使用 Apple 提供的安全 API（如 LocalAuthentication、CryptoKit）
2. **最小权限原则**：只请求应用必需的权限
3. **数据保护**：使用文件保护和密钥链存储敏感数据
4. **安全启动验证**：利用 App Attest 验证应用完整性

### 22.2 对安全研究者的建议

1. **关注 IPC 层**：xnuproxy 和 Tightbeam 是新的攻击面
2. **研究 Conclave 接口**：Conclave 与外部的接口可能存在漏洞
3. **侧信道研究**：硬件隔离可能存在侧信道泄露
4. **SPTM 实现分析**：SPTM 代码本身可能存在漏洞
5. **启动链分析**：安全启动链的实现可能存在弱点

### 22.3 对企业的建议

1. **部署 Lockdown Mode**：为高风险用户启用锁定模式
2. **设备管理**：使用 MDM 管理企业设备的安全配置
3. **监控异常行为**：监控设备上的异常 IPC 调用和内存访问
4. **及时更新**：保持设备和应用的最新状态

## 23. 未来演进方向

### 23.1 可能的架构演进

基于当前的架构趋势，未来可能出现：

1. **更多 Conclave**：更多敏感服务被迁移到 Conclave 中
2. **更强的隔离**：GL 级别可能进一步细分
3. **形式化验证**：关键组件可能经过形式化安全验证
4. **硬件扩展**：SPRR/GXF 可能在未来的 Apple Silicon 中增强

### 23.2 对安全生态的影响

1. **漏洞利用成本上升**：完整的 exploit chain 需要更多层次的漏洞
2. **攻击面转移**：攻击者将更多关注 IPC 层和 Conclave 接口
3. **安全研究机会**：新的架构带来新的研究课题
4. **隐私保护增强**：用户敏感数据获得更强的保护

### 23.3 行业影响

Apple 的分区化安全架构可能影响整个行业：

- **Android 厂商**：可能采用类似的隔离机制
- **ARM 架构**：可能在标准 ARM 特性中加入类似功能
- **安全标准**：可能推动新的安全评估标准

## 24. 总结

Apple 的 SPTM、TXM 和 Exclaves 代表了移动操作系统安全架构的一次根本性变革。从单体内核的单极信任模型，转向分区化的多域信任模型，这一变革从根本上改变了内核漏洞的价值和攻击者面临的挑战。

**核心要点**：

1. **SPTM** 作为内存重类型化的唯一权威，通过 GL2 级别的硬件隔离确保其不可被绕过
2. **TXM** 将代码签名验证从内核中独立出来，防止内核妥协导致签名验证失效
3. **Exclaves** 将敏感服务隔离到 Conclave 中，即使内核被攻破，敏感数据仍然不可达
4. **三层协同** 提供了纵深防御，每一层都需要独立的漏洞利用才能突破
5. **攻击面缩减** 使得内核漏洞的价值从"完全控制"降级为"部分控制"

这一架构变革的意义超越了 Apple 平台本身，为整个移动安全行业指明了方向：未来的安全架构将更加注重分区化隔离和最小权限原则，即使在高特权级别被攻破的情况下，仍然能够保护最敏感的数据和功能。
