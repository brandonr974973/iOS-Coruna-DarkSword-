## 1. 概述

### 1.1 什么是 PAC

指针认证码（Pointer Authentication Code, PAC）是 ARM 在 ARMv8.3-A 架构中引入的硬件级安全扩展，旨在对抗内存损坏漏洞中最具威胁的攻击类型：控制流劫持。PAC 通过对指针值进行密码学签名，使处理器能够在运行时验证指针的完整性和来源合法性，从而在硬件层面阻止攻击者篡改函数返回地址、函数指针和关键数据结构中的指针。

### 1.2 PAC 的诞生背景

在 PAC 出现之前，对抗控制流劫持主要依赖以下软件级防御：

| 防御机制 | 原理 | 局限 |
|----------|------|------|
| Stack Canary | 在栈帧中插入随机值，函数返回前验证 | 可被信息泄露绕过 |
| ASLR | 随机化内存布局 | 可被信息泄露或暴力破解绕过 |
| DEP/NX | 禁止执行不可执行页面的代码 | 无法阻止 ROP/JOP |
| CFI（软件级） | 验证间接跳转目标的合法性 | 性能开销大，覆盖不完整 |

这些软件防御的共同问题是：它们要么可以被信息泄露绕过，要么性能开销过高，要么覆盖范围不完整。PAC 将指针完整性验证下沉到硬件层面，提供了更强的安全保障和更低的性能开销。

### 1.3 Apple 的采用时间线

| 时间 | 事件 |
|------|------|
| 2018 年 | ARM 发布 ARMv8.3-A，引入 PAC 扩展 |
| 2018 年 | Apple A12 Bionic 芯片首次实现 PAC（iPhone XS/XR） |
| 2019 年 | iOS 13 内核开始启用 PAC 保护 |
| 2020 年 | A14 芯片增强 PAC 实现 |
| 2021 年 | iOS 15 扩大 PAC 覆盖范围至用户态关键路径 |
| 2022-2023 年 | A16/A17 芯片持续优化 PAC 性能 |
| 2024 年 | M 系列芯片（M1-M4）同样支持 PAC |

### 1.4 PAC 在 iOS 安全架构中的位置

```
┌──────────────────────────────────────────────┐
│              应用层                            │
│  ┌──────────────────────────────────────┐    │
│  │  用户态 PAC（函数指针、vtable 等）     │    │
│  └──────────────────────────────────────┘    │
├──────────────────────────────────────────────┤
│              内核态                            │
│  ┌──────────────────────────────────────┐    │
│  │  内核 PAC（返回地址、函数指针、         │    │
│  │  关键数据结构指针）                     │    │
│  └──────────────────────────────────────┘    │
├──────────────────────────────────────────────┤
│              硬件层                            │
│  ┌──────────────────────────────────────┐    │
│  │  PAC 签名/验证引擎（QARMA 算法）       │    │
│  │  密钥存储（密钥对用户态/内核态不可见）   │    │
│  └──────────────────────────────────────┘    │
├──────────────────────────────────────────────┤
│  ASLR │ KTRR │ PPL │ AMFI │ Sandbox         │
└──────────────────────────────────────────────┘
```

## 2. PAC 的硬件基础：ARMv8.3-A 指针认证扩展

### 2.1 ARM 地址空间利用

ARMv8（AArch64）使用 64 位指针，但实际虚拟地址空间远小于 64 位：

| 配置 | 虚拟地址位数 | 实际地址空间 |
|------|-------------|-------------|
| 39 位 VA | 39 | 512 GB |
| 48 位 VA | 48 | 256 TB |
| 52 位 VA（LVA） | 52 | 4 PB |

以 iOS 设备常用的 39 位或 48 位虚拟地址为例，64 位指针中有大量高位未被使用：

```
64 位指针格式：
┌──────────────────┬──────────────────────────────┐
│   未使用的高位    │        实际虚拟地址            │
│  (可用于存储 PAC) │                              │
└──────────────────┴──────────────────────────────┘

以 48 位 VA 为例：
┌────────────────┬────────────────────────────────┐
│ 16 位 (PAC)    │ 48 位 (实际地址)                │
└────────────────┴────────────────────────────────┘
```

PAC 利用这些未使用的高位存储密码学签名。对于内核指针（通常使用更高的地址范围），PAC 也可以存储在低位的未使用位中。

### 2.2 地址空间布局

iOS 中的虚拟地址空间分配：

| 区域 | 地址范围（典型） | 说明 |
|------|------------------|------|
| 用户态代码 | 0x0000000000000000 - 0x0000008000000000 | 应用和系统框架 |
| 用户态堆 | 动态分配 | malloc 区域 |
| 用户态栈 | 动态分配 | 线程栈 |
| 内核态代码 | 0xFFFFFFF000000000+ | XNU 内核 |
| 内核态数据 | 内核数据区域 | 内核堆和全局数据 |

PAC 在不同区域使用不同的存储位置：
- 用户态指针：PAC 存储在高位（TBI = Top Byte Ignore 区域）
- 内核态指针：PAC 可能存储在高位或低位，取决于地址布局

### 2.3 TBI（Top Byte Ignore）

ARMv8 的 TBI 特性允许硬件在地址转换时忽略指针的最高字节。这原本用于内存调试工具（如 AddressSanitizer 的 shadow memory 标记）。PAC 复用了这一机制：

- 硬件在地址转换时忽略 PAC 所在的位
- PAC 不影响内存访问的正确性
- 只有在显式验证 PAC 时，才检查签名的有效性

## 3. PAC 核心原理：密码学指针签名

### 3.1 签名过程

PAC 的签名过程可以形式化描述为：

```
PAC = QARMA(Key, Modifier, Pointer)
```

其中：
- **Key**：硬件密钥，对软件不可见。不同特权级和上下文使用不同的密钥
- **Modifier**：上下文值（Context），用于绑定指针到特定的使用场景
- **Pointer**：被签名的指针值
- **QARMA**：Apple 选择的轻量级密码算法

签名结果（PAC）被嵌入到指针的未使用位中，生成"认证指针"：

```
认证指针 = {PAC, 原始地址}
```

### 3.2 验证过程

验证是签名的逆操作：

```
1. 从认证指针中提取 PAC 和地址
2. 使用相同的 Key 和 Modifier 重新计算 PAC'
3. 比较 PAC 和 PAC'
4. 如果匹配 → 指针合法
5. 如果不匹配 → 触发异常（SIGBUS/SIGSEGV）
```

### 3.3 签名强度

| 参数 | 值 | 说明 |
|------|-----|------|
| PAC 长度 | 约 16 位（部分实现可达更多） | 存储在指针的未使用位中 |
| 暴力破解概率 | 1/2^16 ≈ 1/65536 | 单次随机猜测的成功率 |
| 密钥长度 | 128 位 | 硬件内部密钥 |
| 算法 | QARMA（轻量级分组密码） | 专为硬件实现优化 |

16 位的 PAC 意味着攻击者随机猜测的成功率约为 1/65536。虽然看似不高，但在大量尝试的场景下（如内核漏洞利用中的暴力破解），这个概率会累积。这也是为什么 PAC 需要与其他防御机制（如 KASLR、暴力破解缓解）协同工作。

### 3.4 签名不可伪造性

PAC 的安全属性：

- **不可伪造**：不知道密钥的情况下，无法为任意指针生成有效的 PAC
- **上下文绑定**：PAC 与 Modifier 绑定，不能将一个上下文的有效 PAC 用于另一个上下文
- **指针绑定**：PAC 与原始指针值绑定，修改指针地址后 PAC 失效
- **密钥隔离**：密钥存储在硬件中，即使内核被攻破也无法直接提取密钥

## 4. PAC 指令集详解

### 4.1 指令分类

ARMv8.3-A PAC 扩展引入了以下指令：

**指针签名指令（Pointer Authentication Instructions）**：

| 指令 | 功能 | 使用的密钥 |
|------|------|-----------|
| PACIA | 使用 A 密钥签名指令指针 | APIAKey |
| PACIB | 使用 B 密钥签名指令指针 | APIBKey |
| PACDA | 使用 A 密钥签名数据指针 | APDAKey |
| PACIA1716 | 使用 X17 作为上下文的 PACIA | APIAKey |
| PACIASP | 使用 SP 作为上下文的 PACIA | APIAKey |
| PACIBSP | 使用 SP 作为上下文的 PACIB | APIBKey |

**指针验证指令**：

| 指令 | 功能 | 使用的密钥 |
|------|------|-----------|
| AUTIA | 使用 A 密钥验证指令指针 | APIAKey |
| AUTIB | 使用 B 密钥验证指令指针 | APIBKey |
| AUTDA | 使用 A 密钥验证数据指针 | APDAKey |
| AUTIA1716 | 使用 X17 作为上下文的 AUTIA | APIAKey |
| AUTIASP | 使用 SP 作为上下文的 AUTIA | APIAKey |
| AUTIBSP | 使用 SP 作为上下文的 AUTIB | APIBKey |

** Strip 指令（去除 PAC）**：

| 指令 | 功能 |
|------|------|
| XPACI | 去除指令指针的 PAC（不验证） |
| XPACD | 去除数据指针的 PAC（不验证） |

**通用密钥签名**：

| 指令 | 功能 |
|------|------|
| PACGA | 生成两个值之间的通用认证码 |

### 4.2 典型使用模式

**函数返回地址保护**：

```assembly
; 函数序言（prologue）
; LR（链接寄存器）包含返回地址
PACIASP    ; 用 APIAKey 签名 LR，上下文为 SP
           ; 签名后的 LR 存储在 LR 中

; ... 函数体 ...

; 函数尾声（epilogue）
AUTIASP    ; 用 APIAKey 验证 LR，上下文为 SP
           ; 如果验证失败，将 LR 高位设为错误码
RET        ; 跳转到 LR（已验证的返回地址）
```

**函数指针保护**：

```assembly
; 签名函数指针
; X0 = 函数地址, X1 = 上下文值
PACIA X0, X1    ; 用 APIAKey 签名 X0，上下文为 X1

; 使用函数指针
; X0 = 认证后的函数指针, X1 = 上下文值
AUTIA X0, X1    ; 验证 X0
BLR X0          ; 跳转到验证后的地址
```

### 4.3 验证失败行为

当 PAC 验证失败时：

1. 硬件不会立即触发异常
2. 而是将指针的高位设置为特定的错误标记
3. 当 CPU 尝试跳转到被标记的指针时，触发异常
4. 操作系统收到异常信号（通常是 SIGBUS 或 SIGSEGV）

这种延迟失败的设计允许软件在某些情况下处理验证失败，而不是立即崩溃。

## 5. 密钥体系与上下文设计

### 5.1 密钥层次结构

iOS 中使用多组 PAC 密钥，形成层次化的保护体系：

```
┌─────────────────────────────────────────┐
│            硬件密钥存储                    │
│  ┌─────────────────────────────────┐    │
│  │  用户态密钥                       │    │
│  │  ├── APIAKey_EL0 (指令指针 A)    │    │
│  │  ├── APIBKey_EL0 (指令指针 B)    │    │
│  │  └── APDAKey_EL0 (数据指针 A)    │    │
│  ├─────────────────────────────────┤    │
│  │  内核态密钥                       │    │
│  │  ├── APIAKey_EL1 (指令指针 A)    │    │
│  │  ├── APIBKey_EL1 (指令指针 B)    │    │
│  │  └── APDAKey_EL1 (数据指针 A)    │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

关键特性：
- 用户态和内核态使用不同的密钥
- 密钥在每次启动时随机生成
- 密钥对软件完全不可见（没有加载/存储密钥的指令）
- 密钥在 CPU 重置时重新生成

### 5.2 上下文（Modifier）设计

上下文值是 PAC 安全性的关键组成部分。它将指针绑定到特定的使用场景，防止指针在不同上下文中被重用。

**常用上下文类型**：

| 上下文类型 | 值 | 用途 |
|-----------|-----|------|
| SP（栈指针） | 当前 SP 值 | 函数返回地址保护 |
| X17 | X17 寄存器值 | 通用函数指针 |
| 地址本身 | 指针地址 | 某些数据指针 |
| 零值 | 0 | 无上下文绑定（较弱） |

**SP 作为上下文的安全意义**：

使用 SP 作为函数返回地址的上下文值，将返回地址绑定到特定的栈帧位置。这防止了以下攻击：
- 将函数 A 的返回地址移动到函数 B 的栈帧
- 重用旧栈帧中的返回地址（栈重用攻击）
- 跨函数复制返回地址

### 5.3 密钥轮换

| 事件 | 密钥行为 |
|------|----------|
| 设备重启 | 所有 PAC 密钥重新随机生成 |
| 进程创建 | 继承当前系统密钥 |
| 特权级切换 | 自动切换到对应特权级的密钥 |
| 运行时 | 密钥不变（无运行时轮换） |

## 6. Apple 的 PAC 实现：QARMA 密码算法

### 6.1 QARMA 算法概述

QARMA 是一种专为硬件实现优化的轻量级分组密码（tweakable block cipher），由 Google 的 researchers 设计。Apple 选择 QARMA 作为 PAC 的底层密码算法。

### 6.2 QARMA 特性

| 参数 | 值 |
|------|-----|
| 分组大小 | 64 位 |
| 密钥大小 | 128 位 |
| Tweak 大小 | 64 位 |
| 轮数 | 7 轮（QARMA-64） |
| 硬件面积 | 约 2.5K GE |
| 延迟 | 约 3-5 个时钟周期 |

### 6.3 QARMA 在 PAC 中的映射

在 PAC 的上下文中，QARMA 的参数映射如下：

| QARMA 参数 | PAC 映射 |
|-----------|----------|
| 明文输入 | 指针地址（部分位） |
| Tweak | 上下文值（Modifier） |
| 密钥 | 硬件 PAC 密钥 |
| 密文输出 | PAC 值（截取高位） |

### 6.4 硬件实现优化

Apple 对 QARMA 的硬件实现进行了深度优化：

- **流水线化**：PAC 计算与指令执行流水线重叠，减少延迟
- **并行计算**：多个 PAC 操作可以并行执行
- **低功耗设计**：针对移动设备的功耗约束优化
- **面积优化**：最小化芯片面积占用

### 6.5 PAC 计算延迟

根据公开的性能分析数据：

| 操作 | 延迟（估计） |
|------|-------------|
| PACIA（签名指令指针） | ~3-5 时钟周期 |
| AUTIA（验证指令指针） | ~3-5 时钟周期 |
| PACDA（签名数据指针） | ~3-5 时钟周期 |
| XPACI（去除 PAC） | ~1 时钟周期 |

## 7. 编译器支持：Clang/LLVM 中的 PAC

### 7.1 编译器标志

Clang/LLVM 提供以下 PAC 相关的编译选项：

| 标志 | 功能 |
|------|------|
| `-mbranch-protection=pac-ret` | 为函数返回地址启用 PAC |
| `-mbranch-protection=standard` | 启用标准分支保护（PAC + BTI） |
| `-msign-return-address=all` | 对所有函数签名返回地址 |
| `-msign-return-address=non-leaf` | 仅对非叶函数签名返回地址 |

### 7.2 自动保护范围

当启用 `-mbranch-protection=pac-ret` 时，编译器自动：

1. 在每个函数的序言中插入 `PACIASP`（或 `PACIBSP`）
2. 在每个函数的尾声中插入 `AUTIASP`（或 `AUTIBSP`）
3. 对间接分支目标插入验证指令
4. 在函数指针调用前插入验证

### 7.3 手动 PAC 使用

开发者可以通过内联汇编或编译器内置函数手动使用 PAC：

```c
// 签名函数指针
void *signed_ptr = __builtin_pacia((void *)func, context);

// 验证函数指针
void *verified_ptr = __builtin_autia(signed_ptr, context);

// 签名数据指针
void *signed_data = __builtin_pacda(data_ptr);

// 去除 PAC（不验证）
void *stripped = __builtin_xpaci(ptr);
```

### 7.4 Apple 的编译器定制

Apple 对 Clang/LLVM 进行了定制，在 iOS 系统构建中：

- 内核（XNU）编译时启用 PAC 保护
- 系统框架编译时启用 PAC 保护
- 使用自定义的上下文策略
- 对关键数据结构中的指针进行手动签名

## 8. iOS 内核中的 PAC 应用

### 8.1 内核返回地址保护

XNU 内核中所有函数编译时启用 PAC，保护函数返回地址：

```
函数调用链：
userspace → trap → kernel_entry → function_A → function_B
                                          ↑
                                    LR 被 PACIASP 签名
                                          ↓
function_B 返回 → AUTIASP 验证 LR → 返回 function_A
```

### 8.2 内核数据结构保护

内核中关键数据结构中的指针使用 PAC 签名：

**vtable 指针**：

C++ 对象的虚函数表指针是攻击者的高价值目标。内核中的 C++ 对象（如 IOKit 对象）的 vtable 指针经过 PAC 签名：

```cpp
class OSObject {
    // vtable 指针被 PAC 签名
    // 攻击者无法直接替换 vtable 指针
    virtual void retain();
    virtual void release();
};
```

**函数指针结构**：

内核中的函数指针结构（如文件操作表、网络协议操作等）中的函数指针使用 PAC 签名：

```c
struct fileops {
    int (*fo_read)(struct fileproc *, ...);   // PAC 签名
    int (*fo_write)(struct fileproc *, ...);  // PAC 签名
    int (*fo_close)(struct fileproc *, ...);  // PAC 签名
};
```

**链表指针**：

内核链表结构中的前向/后向指针可能使用 PAC 签名，防止攻击者修改链表结构：

```c
struct list_head {
    struct list_head *next;  // 可能使用 PAC 签名
    struct list_head *prev;  // 可能使用 PAC 签名
};
```

### 8.3 内核中的 PAC 密钥使用

| 密钥 | 用途 |
|------|------|
| APIAKey_EL1 | 内核函数返回地址、内核函数指针 |
| APIBKey_EL1 | 特定内核子系统（如安全相关） |
| APDAKey_EL1 | 内核数据指针（链表、vtable 等） |

### 8.4 内核 PAC 覆盖范围

| 组件 | PAC 保护 | 说明 |
|------|----------|------|
| 函数返回地址 | 是 | 所有内核函数 |
| IOKit vtable | 是 | C++ 虚函数表 |
| 文件操作表 | 是 | VFS 层函数指针 |
| 网络协议操作 | 是 | socket 操作函数指针 |
| 中断处理表 | 是 | 中断向量 |
| 系统调用表 | 部分 | 关键入口点 |
| 页表指针 | 否 | 由 MMU 硬件保护 |

## 9. 用户态 PAC 保护

### 9.1 用户态 PAC 的启用

从 iOS 15 开始，Apple 逐步扩大用户态 PAC 的覆盖范围：

- 系统框架（libsystem、Foundation 等）启用 PAC
- 关键系统守护进程启用 PAC
- 第三方应用根据编译设置可选启用

### 9.2 用户态保护范围

| 保护对象 | 说明 |
|----------|------|
| 函数返回地址 | 用户态函数调用链 |
| Objective-C 方法调度 | objc_msgSend 中的 IMP 指针 |
| C++ vtable | 用户态 C++ 对象 |
| 回调函数指针 | 事件处理回调 |
| 信号处理函数 | signal handler 地址 |

### 9.3 Objective-C 运行时与 PAC

Objective-C 的消息发送机制（`objc_msgSend`）是用户态的关键攻击面。Apple 对 `objc_msgSend` 中的 IMP（方法实现指针）使用 PAC 签名：

```
objc_msgSend 流程：
1. 从对象 isa 指针获取类信息
2. 从方法缓存查找 SEL → IMP 映射
3. IMP 指针经过 PAC 签名
4. 调用前验证 IMP 的 PAC
5. 跳转到验证后的 IMP
```

这防止了攻击者通过修改方法缓存或 isa 指针来劫持 Objective-C 方法调用。

### 9.4 dyld 与 PAC

动态链接器（dyld）中的关键指针也使用 PAC 保护：

- 符号绑定中的函数指针
- lazy binding 的 stub 地址
- 重定位表中的指针

## 10. PAC 对攻击面的影响分析

### 10.1 被 PAC 阻断的攻击技术

**经典 ROP（Return-Oriented Programming）**：

```
攻击目标：覆盖栈上的返回地址
PAC 防御：返回地址经过 PAC 签名
          修改后的返回地址 PAC 验证失败
          跳转到被篡改的地址触发异常
结果：经典 ROP 被 PAC 有效阻断
```

**JOP（Jump-Oriented Programming）**：

```
攻击目标：修改函数指针或 vtable 指针
PAC 防御：函数指针经过 PAC 签名
          修改后的指针 PAC 验证失败
结果：直接 JOP 被 PAC 阻断
```

**栈溢出覆盖返回地址**：

```
攻击目标：利用栈缓冲区溢出覆盖返回地址
PAC 防御：即使覆盖了返回地址，PAC 验证失败
结果：栈溢出仍然可以破坏数据，但无法劫持控制流
```

**堆溢出覆盖函数指针**：

```
攻击目标：利用堆溢出覆盖对象中的函数指针
PAC 防御：函数指针经过 PAC 签名
          覆盖后的指针 PAC 验证失败
结果：堆溢出仍然可以破坏数据，但无法直接劫持控制流
```

### 10.2 PAC 未覆盖的攻击面

**数据-only 攻击**：

PAC 只保护指针的完整性，不保护数据。攻击者仍然可以：
- 修改安全关键的整数变量（如权限标志）
- 修改安全策略数据
- 修改加密密钥或令牌
- 修改配置数据

**信息泄露**：

PAC 不防止信息泄露。攻击者仍然可以：
- 读取内存中的敏感数据
- 泄露指针值（包括 PAC 值）
- 利用泄露的信息构造进一步的攻击

**非指针 corruption**：

PAC 只保护指针，不保护其他类型的数据：
- 整数溢出/下溢
- 布尔值翻转
- 字符串内容修改

### 10.3 攻击面量化分析

| 攻击技术 | PAC 前 | PAC 后 | 说明 |
|----------|--------|--------|------|
| 栈溢出 → ROP | 可行 | 不可行 | 返回地址被保护 |
| 堆溢出 → 函数指针 | 可行 | 不可行 | 函数指针被保护 |
| UAF → vtable 替换 | 可行 | 不可行 | vtable 指针被保护 |
| 类型混淆 → 函数指针 | 可行 | 不可行 | 函数指针被保护 |
| 信息泄露 → 任意地址执行 | 可行 | 受限 | 需要有效 PAC |
| 数据-only 攻击 | 可行 | 可行 | PAC 不保护数据 |

## 11. PAC 绕过技术：攻击者的对策

### 11.1 PAC 预测/暴力破解

由于 PAC 只有约 16 位，攻击者可以尝试暴力破解：

**原理**：

- PAC 空间为 2^16 = 65536 种可能
- 如果攻击者可以反复尝试不同的 PAC 值
- 平均需要约 32768 次尝试即可成功

**适用条件**：

- 进程不会在每次 PAC 验证失败后终止
- 攻击者可以观察验证结果（成功/失败）
- 目标地址是已知的

**iOS 的缓解**：

- 内核态：PAC 验证失败通常导致内核恐慌（系统重启）
- 用户态：进程收到 SIGBUS 信号终止
- 限制了暴力破解的可行性

### 11.2 PAC 泄露与重用

**PAC 泄露**：

如果攻击者可以通过信息泄露获取有效的认证指针（包括 PAC），则可以直接使用该指针：

```
信息泄露 → 获取有效的认证函数指针 → 直接使用
```

**PAC 重用**：

在同一上下文中，相同的指针值总是产生相同的 PAC。如果攻击者可以：
1. 获取某个有效指针的 PAC
2. 将相同的 PAC 应用到另一个相同地址的指针
3. 在相同的上下文中使用该指针

则 PAC 验证将通过。

### 11.3 签名预言机（Signing Oracle）

如果攻击者可以找到一种方式让系统为攻击者选择的指针值签名，则可以利用系统作为签名预言机：

```
攻击者选择的指针值 → 系统签名 → 攻击者获取有效 PAC
```

这需要找到代码中不当地使用 PAC 签名的位置。

### 11.4 XPAC 攻击

XPAC（eXecute PAC）是一种利用 PAC 验证失败行为的攻击技术：

**原理**：

当 PAC 验证失败时，硬件不会立即触发异常，而是将指针的高位设置为错误标记。如果攻击者可以：

1. 触发 PAC 验证失败
2. 在异常发生前利用被标记的指针
3. 通过某种方式清除错误标记

则可能绕过 PAC 检查。

**实际可行性**：

在 Apple 的实现中，PAC 验证失败后的行为被设计为安全的：被标记的指针在跳转时会触发异常，没有窗口期可以利用。

### 11.5 上下文混淆攻击

如果攻击者可以控制 PAC 的上下文值（Modifier），则可能将指针从一个上下文转移到另一个上下文：

```
指针 P 在上下文 C1 中被签名
攻击者使系统在上下文 C2 中验证 P
如果 C1 == C2，则验证通过
```

这需要找到上下文值可以被攻击者控制或预测的场景。

### 11.6 同地址重用攻击

PAC 绑定的是指针地址而非指针指向的内容。如果：

1. 一个有效的函数指针被签名
2. 函数指针指向的内存被释放
3. 攻击者在该地址分配新的恶意数据
4. 原始签名指针仍然有效（PAC 仍然匹配）

则攻击者可以通过原始签名指针跳转到恶意数据。

### 11.7 内核利用中的 PAC 绕过实例

在现代 iOS 越狱和漏洞利用中，攻击者采用以下策略绕过 PAC：

**策略一：避免控制流劫持**

既然 PAC 使控制流劫持变得困难，攻击者转向 data-only 攻击：
- 不修改控制流
- 只修改安全关键的数据
- 例如修改 cred 结构中的 UID

**策略二：利用未受保护的指针**

并非所有指针都受 PAC 保护：
- 某些遗留代码路径未编译 PAC
- 某些数据结构中的指针未被签名
- 第三方内核扩展（如果有）可能未启用 PAC

**策略三：利用 PAC 密钥的局限性**

- PAC 密钥在启动后不变
- 如果攻击者可以计算或推导密钥关系
- 可能跨上下文构造有效 PAC

**策略四：组合漏洞链**

现代 iOS 利用通常需要组合多个漏洞：
1. 信息泄露漏洞 → 获取内存布局和 PAC 值
2. 内存损坏漏洞 → 修改数据（非控制流）
3. 逻辑漏洞 → 利用修改后的数据达到目标

## 12. PAC 与 CFI 的关系

### 12.1 CFI 概述

控制流完整性（Control Flow Integrity, CFI）是一种安全机制，确保程序的控制流遵循预定义的正常执行路径。CFI 分为前向 CFI（保护函数调用）和后向 CFI（保护函数返回）。

### 12.2 PAC 作为硬件 CFI

PAC 可以被视为一种硬件级 CFI 实现：

| 维度 | 软件 CFI | PAC（硬件 CFI） |
|------|----------|-----------------|
| 前向 CFI | 类型检查、间接调用验证 | PAC 签名函数指针 |
| 后向 CFI | Shadow Stack | PAC 签名返回地址 |
| 性能开销 | 5-15% | < 1% |
| 覆盖完整性 | 取决于实现 | 硬件保证 |
| 安全性 | 可被绕过（如 Gadget 复用） | 密码学保证 |

### 12.3 BTI（Branch Target Identification）

BTI 是 ARMv8.5-A 引入的另一项分支保护扩展，与 PAC 互补：

**PAC**：验证指针的来源（是否被合法签名）
**BTI**：验证跳转目标的入口（是否标记为合法的跳转目标）

```
BTI 工作原理：
1. 编译器在合法跳转目标处插入 BTI 指令（landing pad）
2. 间接分支（BR/BLR）到达非 BTI 标记的地址时触发异常
3. 防止攻击者跳转到函数中间的 gadget
```

Apple A14 及后续芯片支持 BTI，与 PAC 共同提供完整的分支保护。

### 12.4 PAC + BTI 的联合保护

```
攻击场景：ROP/JOP
PAC 防御：返回地址和函数指针被签名 → 无法伪造
BTI 防御：只能跳转到 BTI landing pad → 无法使用中间 gadget

联合效果：
- PAC 阻止伪造指针
- BTI 阻止使用非预期入口点
- 两者结合提供最强的控制流保护
```

## 13. PAC 在越狱攻防中的角色

### 13.1 PAC 对越狱的影响

PAC 的引入显著提高了 iOS 越狱的难度：

**PAC 前的越狱（iOS 12 及更早）**：

- 典型的越狱路径：内核信息泄露 → 内核栈/堆溢出 → 覆盖函数指针 → 内核代码执行
- 控制流劫持是越狱的核心步骤
- 一旦劫持控制流，就可以禁用代码签名、挂载文件系统

**PAC 后的越狱（iOS 13+）**：

- 控制流劫持被 PAC 阻断
- 越狱社区被迫转向 data-only 攻击
- 需要找到不依赖控制流劫持的内核代码执行路径
- 越狱工具的开发周期显著延长

### 13.2 现代越狱策略

| 越狱工具 | 策略 | 说明 |
|----------|------|------|
| checkra1n | 硬件漏洞（checkm8） | 绕过所有软件保护 |
| unc0ver | 数据-only + 逻辑漏洞 | 避免控制流劫持 |
| Taurine | 数据-only + 信息泄露 | 组合多个漏洞 |
| Dopamine | PAC-aware 利用技术 | 针对 PAC 的绕过策略 |

### 13.3 越狱中的 PAC 绕过实践

**PAC 绕过策略一：利用 PAC 未覆盖的路径**

某些内核路径中的指针可能未被 PAC 保护：
- 遗留代码路径
- 特定驱动程序的回调
- 未更新的内核数据结构

**PAC 绕过策略二：PAC 泄露 + 重用**

1. 利用信息泄露获取内核中已签名的指针
2. 将签名的指针重用到攻击者控制的数据
3. 利用已签名的指针劫持控制流

**PAC 绕过策略三：数据-only 提权**

1. 利用堆溢出修改进程 cred 结构
2. 将 UID 修改为 0（root）
3. 不修改任何控制流指针
4. PAC 无法阻止数据修改

### 13.4 越狱社区的技术演进

PAC 推动了越狱社区的技术演进：

- 从控制流劫持转向数据操作
- 更依赖信息泄露漏洞
- 更深入理解内核数据结构
- 更精细的漏洞利用工程
- 对 PAC 实现细节的深入分析

## 14. PAC 的性能开销分析

### 14.1 理论开销

PAC 的性能开销主要来自：

| 开销来源 | 说明 |
|----------|------|
| 签名计算 | 每次签名需要 QARMA 计算（~3-5 周期） |
| 验证计算 | 每次验证需要 QARMA 计算（~3-5 周期） |
| 代码大小增加 | 额外的 PAC 指令增加代码体积 |
| 流水线影响 | PAC 指令可能影响指令流水线 |

### 14.2 实测性能数据

根据公开的性能基准测试：

| 场景 | 性能开销 |
|------|----------|
| SPEC CPU 2017（整数） | < 1% |
| SPEC CPU 2017（浮点） | < 0.5% |
| 内核上下文切换 | < 2% |
| 系统调用密集工作负载 | 2-5% |
| 整体用户体验 | 不可感知 |

### 14.3 与软件 CFI 的对比

| 方案 | 性能开销 | 安全性 |
|------|----------|--------|
| 软件 CFI（如 CFIVerifier） | 5-15% | 中等 |
| Intel CET | 1-3% | 中等 |
| ARM PAC | < 1% | 高（密码学保证） |
| PAC + BTI | 1-2% | 最高 |

### 14.4 Apple 的优化策略

Apple 通过以下策略最小化 PAC 的性能影响：

- **选择性签名**：不是所有函数都签名返回地址，叶函数（不调用其他函数的函数）可能跳过签名
- **硬件加速**：QARMA 在硬件中实现，延迟极低
- **流水线重叠**：PAC 计算与内存访问重叠
- **编译器优化**：编译器智能选择签名策略，避免不必要的签名

## 15. PAC 调试与逆向工程

### 15.1 PAC 对调试的影响

PAC 给调试带来了新的挑战：

**指针显示**：

调试器显示指针时需要处理 PAC：
- 原始指针值包含 PAC
- 需要去除 PAC 才能显示有效地址
- GDB/LLDB 需要支持 PAC 感知的指针显示

**断点设置**：

PAC 不影响断点设置，因为断点使用软件中断（BRK），不涉及指针签名。

**单步执行**：

单步执行 PAC 保护的代码时，需要注意：
- 签名和验证指令的行为
- 验证失败时的指针状态
- 错误标记的含义

### 15.2 LLDB 中的 PAC 支持

LLDB（Apple 的调试器）提供以下 PAC 相关功能：

```
# 查看指针的 PAC 值
(lldb) p/x $lr
# 输出包含 PAC 的完整值

# 去除 PAC 显示有效地址
(lldb) p/x $lr & 0x0000FFFFFFFFFFFF
# 输出去除 PAC 后的地址

# 检查 PAC 验证状态
(lldb) register read lr
# 显示完整的 LR 寄存器值
```

### 15.3 逆向工程中的 PAC

**IDA Pro / Ghidra 支持**：

现代逆向工程工具已经支持 PAC 指令的反汇编：

```assembly
; IDA Pro 反汇编输出
PACIASP          ; 签名返回地址
; ... 函数体 ...
AUTIASP          ; 验证返回地址
RET
```

**PAC 对 ROP 链构造的影响**：

在 PAC 存在的情况下，传统的 ROP 链构造方法失效：
- 不能简单地覆盖返回地址
- 需要找到已签名的有效指针
- 需要理解上下文约束

### 15.4 PAC 分析工具

| 工具 | 功能 |
|------|------|
| Hopper | 反汇编，支持 PAC 指令 |
| IDA Pro | 反汇编 + 反编译，PAC 感知 |
| Ghidra | 开源反编译，PAC 支持 |
| LLDB | 调试，PAC 寄存器显示 |
| frida | 动态插桩，PAC 感知 |

## 16. PAC 与其他内存安全机制的协同

### 16.1 PAC + ASLR

| 机制 | 保护目标 | 协同效果 |
|------|----------|----------|
| ASLR | 地址随机化 | 攻击者不知道目标地址 |
| PAC | 指针完整性 | 即使知道地址也无法伪造指针 |

协同防御：
- ASLR 防止攻击者预测目标地址
- PAC 防止攻击者伪造有效指针
- 两者结合使控制流劫持几乎不可能

### 16.2 PAC + KTRR（Kernel Text Region Restriction）

| 机制 | 保护目标 |
|------|----------|
| KTRR | 内核代码段只读 |
| PAC | 指针完整性 |

协同防御：
- KTRR 防止修改内核代码
- PAC 防止劫持控制流到非预期位置
- 两者共同保护内核代码完整性

### 16.3 PAC + PPL（Page Protection Layer）

| 机制 | 保护目标 |
|------|----------|
| PPL | 页表完整性 |
| PAC | 指针完整性 |

协同防御：
- PPL 防止修改页表（阻止 arbitrary RW 原语）
- PAC 防止控制流劫持
- 两者共同限制攻击者的能力

### 16.4 PAC + MTE（Memory Tagging Extension）

MTE 是 ARMv8.5-A 引入的另一项安全扩展：

| 机制 | 保护目标 |
|------|----------|
| MTE | 内存安全性（UAF、OOB） |
| PAC | 控制流完整性 |

协同防御：
- MTE 检测内存越界和释放后使用
- PAC 保护指针完整性
- 两者共同覆盖内存损坏的主要攻击面

Apple 目前尚未在 iOS 中启用 MTE，但未来的芯片可能同时支持 PAC 和 MTE。

## 17. PAC 的已知局限性与改进方向

### 17.1 PAC 长度限制

**问题**：

当前 PAC 长度约 16 位，提供 2^16 种可能的签名。虽然单次暴力破解的成功率很低（1/65536），但在以下场景中可能不足：
- 内核利用中的多次尝试
- 无崩溃的验证失败场景

**改进方向**：

- 增加 PAC 长度（需要更多未使用的地址位）
- 使用更大的地址空间（如 52 位 VA）
- 硬件实现优化支持更长的 PAC

### 17.2 上下文粒度

**问题**：

某些场景下上下文值的粒度不够细：
- 使用 SP 作为上下文只绑定到栈帧位置
- 同一栈帧中的多个指针共享相同的上下文
- 攻击者可以在同一栈帧内交换指针

**改进方向**：

- 更细粒度的上下文（如包含函数地址）
- 每个指针使用唯一的上下文
- 硬件支持更复杂的上下文计算

### 17.3 覆盖不完整

**问题**：

并非所有指针都受 PAC 保护：
- 某些遗留代码未编译 PAC
- 某些数据结构中的指针未被签名
- 第三方代码可能未启用 PAC

**改进方向**：

- 扩大 PAC 覆盖范围
- 编译器默认启用 PAC
- 静态分析检测未保护的指针

### 17.4 不保护数据

**问题**：

PAC 只保护指针，不保护数据。Data-only 攻击不受 PAC 影响。

**改进方向**：

- MTE（Memory Tagging Extension）保护内存访问
- 软件级数据完整性检查
- 语言级内存安全（如 Rust、Swift）

### 17.5 密钥管理

**问题**：

PAC 密钥在启动后不变，整个运行期间使用相同的密钥。如果攻击者可以通过侧信道获取密钥信息，则可能伪造 PAC。

**改进方向**：

- 运行时密钥轮换
- 每进程独立密钥
- 侧信道防护增强

## 18. PAC 在 CVE 案例中的攻防实录

### 18.1 CVE-2019-6228（FaceTime 漏洞）

**背景**：iOS 12 中的 FaceTime 漏洞，允许攻击者在对方未接听的情况下听到对方的声音。

**PAC 状态**：此漏洞在 PAC 全面启用之前被发现和利用。

**启示**：PAC 不防止逻辑漏洞，只防止内存损坏导致的控制流劫持。

### 18.2 CVE-2021-30860（FORCEDENTRY）

**背景**：NSO Group 的 Pegasus 间谍软件使用的 iMessage 漏洞。

**PAC 绕过**：

FORCEDENTRY 利用的是 GIF 解码中的整数溢出导致堆缓冲区溢出。在 PAC 启用的设备上：

- 堆溢出可以破坏内存数据
- 但无法直接劫持控制流（PAC 保护函数指针）
- 攻击者需要找到 PAC 未覆盖的路径或使用 data-only 技术

**技术分析**：

FORCEDENTRY 可能使用了以下策略：
1. 利用 PAC 未保护的代码路径
2. 利用信息泄露获取有效 PAC
3. 使用 data-only 攻击达到目标

### 18.3 CVE-2023-38606（S10ldr）

**背景**：影响 iOS 内核的内存损坏漏洞。

**PAC 影响**：

- 漏洞本身可以被利用来破坏内核内存
- 但 PAC 阻止了直接的控制流劫持
- 利用需要额外的步骤来绕过 PAC

### 18.4 CVE-2024-23222（内核信息泄露）

**背景**：内核中的信息泄露漏洞，可能泄露内核内存内容。

**PAC 影响**：

- 信息泄露可以帮助攻击者获取有效的 PAC 值
- 获取的 PAC 可以用于构造有效的认证指针
- 降低了 PAC 的保护效果

### 18.5 越狱工具中的 PAC 分析

**Dopamine 越狱（iOS 15-16.6.1）**：

Dopamine 越狱展示了现代 PAC-aware 利用技术：

1. 使用信息泄露获取内核布局
2. 找到 PAC 未保护的关键数据结构
3. 使用 data-only 攻击修改安全策略
4. 避免直接的控制流劫持

**技术要点**：

- 深入理解 PAC 的覆盖范围
- 找到 PAC 未保护的攻击路径
- 利用 PAC 的局限性而非直接绕过

## 19. PAC 的未来演进

### 19.1 增强的 PAC（Enhanced PAC）

ARM 正在开发增强的 PAC 扩展：

**EPAC（Enhanced PAC）**：

- 更长的 PAC（可能 32 位或更多）
- 更强的密码学保证
- 更细粒度的上下文

**FPAC（Faulting PAC）**：

- PAC 验证失败时立即触发异常
- 不提供错误标记的指针
- 消除 XPAC 攻击的可能性

### 19.2 PAC 与 Rust

Rust 语言的内存安全特性与 PAC 互补：

| 维度 | Rust | PAC |
|------|------|-----|
| 内存安全 | 编译时保证 | 运行时保护 |
| 控制流安全 | 部分（类型系统） | 硬件保证 |
| 覆盖范围 | 安全代码 | 所有代码 |

Apple 正在探索在 iOS 中使用 Rust，PAC 可以为 Rust 代码提供额外的运行时保护。

### 19.3 软件 PAC 模拟

对于不支持 PAC 的旧设备，可以使用软件模拟：

- 在指针中嵌入软件计算的校验和
- 在访问指针时验证校验和
- 性能开销较高，但提供类似的安全保证

### 19.4 PAC 在虚拟化中的扩展

随着 Apple Silicon 在 Mac 上的应用，PAC 在虚拟化环境中的使用正在扩展：

- 虚拟机监控器（Hypervisor）可以为每个虚拟机使用不同的 PAC 密钥
- 虚拟机迁移时需要处理 PAC 密钥的变化
- 嵌套虚拟化中的 PAC 传递

## 20. 总结

### 20.1 PAC 的核心价值

指针认证码（PAC）是 iOS 安全架构中最重要的硬件级防御之一。它通过密码学手段保护指针完整性，在硬件层面阻断了控制流劫持攻击，从根本上改变了 iOS 漏洞利用的游戏规则。

### 20.2 PAC 的安全贡献

| 贡献 | 说明 |
|------|------|
| 阻断经典 ROP/JOP | 返回地址和函数指针被密码学保护 |
| 提高漏洞利用难度 | 攻击者需要更复杂的技术绕过 PAC |
| 降低性能开销 | 硬件实现，开销 < 1% |
| 密码学保证 | 安全性基于密码学假设，而非启发式 |
| 推动攻击技术演进 | 促进 data-only 攻击和更精细的利用技术 |

### 20.3 PAC 的局限性

| 局限 | 说明 |
|------|------|
| PAC 长度有限 | 约 16 位，存在暴力破解风险 |
| 不保护数据 | Data-only 攻击不受影响 |
| 覆盖不完整 | 部分代码路径未启用 PAC |
| 密钥不变 | 运行期间密钥不轮换 |
| 上下文粒度 | 某些场景上下文绑定不够细 |

### 20.4 关键数据

| 指标 | 数值 |
|------|------|
| 首次引入 | ARMv8.3-A（2018） |
| Apple 首次采用 | A12 Bionic（iPhone XS/XR） |
| PAC 长度 | ~16 位 |
| 底层算法 | QARMA（128 位密钥） |
| 单次暴力破解概率 | ~1/65536 |
| 性能开销 | < 1% |
| 密钥数量 | 6 组（用户态 3 + 内核态 3） |

### 20.5 攻防展望

PAC 的引入标志着 iOS 安全进入了一个新时代。攻击者被迫放弃简单的控制流劫持技术，转向更复杂的 data-only 攻击和组合漏洞链。防御者则继续扩展 PAC 的覆盖范围，探索更长的 PAC、更细粒度的上下文和与 MTE 等其他机制的协同。

在可预见的未来，PAC 仍将是 iOS 对抗内存损坏攻击的核心防线，而攻击者与 PAC 的博弈将继续推动移动安全技术的发展。
