## 1. 定位与写法：为什么需要"安全语义"视角

### 1.1 与同系列已有报告的分工

本仓库已经有多份覆盖 iOS 底层的技术文档，它们大多按**子系统**组织：内核架构、文件系统、图形栈、网络栈、驱动框架各成一章，读者得到的是"iOS 由哪些底层部件构成"的地图。其中《iOS 核心底层技术支撑》与《iOS 核心架构与系统层级》两份已经覆盖了子系统巡览，本仓库另有专门讨论执行域隔离、指针认证、内核组件与内核利用的专题文档。

本报告刻意不重复这张地图，而是换一个正交的切法：**按安全原语组织**。同一套底层技术，在子系统视角下回答的是"它怎么工作"，在安全语义视角下回答的是四个不同的问题：

| 维度 | 追问 | 典型失误 |
|------|------|---------|
| **机理** | 这个原语靠什么机制起作用，作用点在哪个执行层 | 把"设计文档里的机制"当成"本机确实在生效的机制" |
| **保证** | 它给出的是强保证（不可绕过）还是弱保证（提高成本） | 把"缓解措施"当成"防线"，据此降低其他层的投入 |
| **边界** | 谁可以豁免它、什么情况下它被关闭、哪一代设备没有它 | 忽略豁免者（entitlement、恢复流程、开发者通路） |
| **观测** | 用户或取证人员能否验证它当时在生效 | 只有事后翻备份才能发现，而备份本身已被篡改 |

这四个维度构成报告的主要骨架。每一章都试图给出"边界"与"观测"两栏，因为它们在公开资料中最常被省略，却正是防守方最需要补上的信息。

### 1.2 为什么要区分"强保证"与"弱保证"

iOS 安全叙事里最大的沟通问题，是把不同强度的机制放在同一张清单上并列陈述。为避免这种误导，本报告对每个原语标注保证强度：

- **G0（结构性保证）**：由硬件或只读启动通路强制，用户与软件层无法关闭，除非物理替换芯片或击穿硬件信任根。例：SEP 内的设备唯一密钥不出芯片边界。
- **G1（可验证保证）**：由系统软件强制执行，但存在**明确、受控、可审计**的豁免者（需要 Apple 私有权限或用户显式操作）。例：代码签名校验。
- **G2（缓解措施）**：显著抬高攻击成本，但不排除成功可能，且常常被合法的兼容性需求削弱。例：ASLR、分配器加固。
- **G3（约定与安全边界）**：主要依赖实现纪律，一旦实现出错即失效。例：XPC 服务端对调用者身份的校验、沙盒配置文件的正确编写。

一个常见误判是：**G2/G3 层的技术含量最高、公开研究最多，因此最容易被当成防线的全部**。真实情况恰恰相反——iOS 上最难被跨越的是 G0/G1，而绝大多数真实入侵案例走的是 G3（实现缺陷）和 G2（信息泄露辅助利用）。本报告的结论章会按这个强度轴重新排序。

### 1.3 威胁模型与读者假设

本报告面向三类读者，写作时保持同一个前提：**只讨论防御侧需要的机理与观测，不提供任何漏洞利用路径、构造方法或可直接用于攻击的细节**。

1. **平台/应用安全工程师**：需要知道哪些底层保证可以依赖、依赖到什么程度，以及如何在自己的产品中观测它们。
2. **移动取证与应急响应人员**：需要知道哪些证据来自底层通路、这些通路在什么配置下被关闭或脱敏。
3. **高价值目标用户**：需要知道设备加固项（锁定模式、开发者模式、诊断数据、恢复流程）到底改变了哪一层保证。

对抗者层级沿用报告系列的通用划分：

- **A1 应用层滥用**：恶意 App、被污染的供应链、过度授权。
- **A2 本地提权者**：已获代码执行，寻求突破沙盒与签名。
- **A3 远程注入者**：零点击/窄点击入口，目标是内核或特权守护进程。
- **A4 物理近距对抗者**：短时间接触设备，寻求解锁、备份或恢复通路。
- **A5 硬件/固件级对抗者**：供应链注入、芯片侧信道、替换外围固件。

### 1.4 版本与机型差异的处理方式

底层支撑机制的引入时间与可用范围高度依赖 iOS 主版本和 SoC 世代。为避免把"某代设备上的机制"错误推广到全部设备，本报告采用如下写法：

- 机制名称与职责按 Apple 官方平台安全文档的表述使用，不复用第三方推测。
- 涉及"较新版本/较新机型才有"的机制，明确标注为条件性存在，并说明**如何在本机确认它是否存在**（观测栏）。
- 不给出无法核实的版本号断言；具体引入版本以 Apple 官方发布说明为准。
- 涉及研究论文而非产品实现的方案（例如微内核重写方向、内存安全驱动语言），明确标注为"研究/演进方向"，不当作现网防线。

## 2. 信任根与密钥层级

### 2.1 机理：设备唯一密钥为什么是关键原语

iOS 的所有静态数据保护、所有可验证启动链条、所有依赖设备身份的密钥派生，最终都落在一组**不出芯片的可编程密钥**上。理解底层支撑的安全语义，第一个必须建立的模型就是密钥层级，而不是加密算法列表。

Apple 的表述里，与设备绑定的根密钥位于 SoC 的加密引擎与 SEP（Secure Enclave Processor）之中，通常被区分为：

- **设备唯一密钥（UID）**：单台设备独有，用于绑定该设备的密钥保护与数据加密链条。设计意图是**只在硬件内部使用**：软件请求加密引擎执行运算，而不是读取密钥本身。
- **分组密钥（GID）**：面向一组设备共享，用于个性化与通用解密场景（例如受 DRM 保护内容的分发）。它的存在说明"信任根"并不是单一密钥，而是一组按用途划分的根。

这两个概念的防御价值在于：数据保护类、钥匙串、FileVault 等价物、iCloud 端到端加密的本地密钥封装，都是在这个层级上**逐级派生**得到的，而不是各子系统各自保存秘密。

### 2.2 机理：密钥层级的逐级封装

一个便于分析的抽象层级（不是内部实现清单）：

```
硬件根（UID / GID，位于 SEP 与加密引擎）
    └── 类密钥 / 元类密钥（按数据保护类划分）
            └── 每文件密钥（per-file key，随文件元数据封装存储）
                    └── 对象级密钥（钥匙串条目、应用容器内文件）
    └── 设备身份密钥（用于验证、MDM 注册、设备 attest）
    └── 用户输入派生（锁屏密码 → 与 UID 结合的解锁路径）
```

关键语义有三点：

1. **解锁是"层级解锁"而不是"密码解密"**：锁屏密码不足以单独解开数据；它必须与硬件内的 UID 结合。因此"知道密码"与"拿到设备"这两个条件在设计上是乘性关系，这也是密码学意义上"离线暴力破解需要真实设备"的原因。
2. **数据保护类决定"什么状态下密钥可用"**：这直接影响取证窗口（见第 2.5 节）。
3. **密钥操作走专用通道**：软件通过安全飞地与加密引擎接口请求运算；这也是为什么 SEP 的固件更新与验证被单独讨论（第 12 章）。

### 2.3 保证：这带来什么，强度多少

| 原语 | 强度 | 实际保证 |
|------|------|---------|
| 设备绑定密钥 | G0 | 密钥明文不进入主处理器可寻址内存；换一台设备无法解出同样的密文 |
| 数据保护类 | G1 | 未解锁状态下受保护类文件不可读；豁免者是"已解锁 + 持有相应权限的进程" |
| 密码与 UID 乘性关系 | G0（结构）+G2（口令强度） | 结构上抗离线爆破，但强度取决于用户口令熵与自动擦除阈值 |
| 密钥层级封装 | G1 | 上层密钥被下层保护；破坏点在实现（错误地把密钥落到弱保护存储）而非模型 |

必须诚实标注的是：**G0 只覆盖"密钥不外泄"这一件事**。它不保证访问控制正确，不保证已解锁状态下的数据不被读取，也不保证应用不把敏感内容写到 `None`/`kSecAttrAccessibleAlways` 一类弱保护位置。

### 2.4 边界：信任根在哪些情况下被削弱

- **解锁状态下**：设备一旦处于"首次解锁后"的窗口内，大量受保护类的密钥驻留在内存中可用。这是数据保护类设计里明确接受的取舍，不是缺陷，但它是防守方最容易低估的边界。
- **备份与同步通路**：iCloud 备份与本地备份是独立于设备加密链条的出口。高级数据保护（ADP）改变的是**云端可见性**，而不是设备本地的类语义；把两者混为一谈会导致错误的风险判断。
- **企业托管通路**：MDM 场景下存在的密钥托管/escrow 类配置，是模型内合法的豁免者。检查设备上是否有无法解释的描述文件，属于信任根审计的一部分。
- **恢复与升级流程**：恢复模式下的固件刷写走的是另一套验证通路（第 12 章）。个性化/授权服务（TSS 类）与 APTicket 构成的是"可安装版本集合"的约束，而不是"数据密钥"的约束；两者不可互相替代。
- **口令熵**：G0 结构无法补偿 4 位数字 PIN。对高价值目标，PIN 长度与"无密码时保留窗口"是信任根实际强度的决定因素。

### 2.5 观测：现场可用的取证窗口与密钥状态

普通用户可确认的部分有限，但下列观察是有意义的：

- **数据保护可访问性**在应用侧可通过钥匙串条目的可访问级别属性表达；开发者应审计自家产品是否使用了"始终可见"级别的条目（该级别在新系统上已被限制或弃用）。
- **取证窗口判断**（应急响应视角）：
  - 设备锁定且未达首次解锁 → 大部分受保护数据对现场取证不可读。
  - 设备已解锁 → 大量数据可访问，且备份可被创建。
  - 设备锁定但已进入"重启动后未解锁"状态 → 保护类之间的差异真正体现出来。
- **托管/描述文件审计**：设置 → 通用 → VPN 与设备管理；命令行侧在具备权限的分析环境中可查看配置描述文件安装清单。任何无法解释的配置文件都应按"存在合法豁免者"处理并上报。
- **密钥使用异常的信号**：钥匙串反复弹认证、应用因无法解密自身数据而重置、系统提示需要 Apple 账户才能继续——都可能是恢复/迁移流程改变了密钥上下文的表征。

### 2.6 常见误判清单

| 误判 | 事实 |
|------|------|
| "端到端加密所以备份里没有数据" | ADP 覆盖的是特定 iCloud 类别；设备本地备份与其他通路需分别分析 |
| "有 SEP 就防住了物理攻击" | SEP 保护密钥与部分敏感运算；解锁窗口、逻辑访问与外设通路不受它管辖 |
| "密码就是加密密钥" | 密码只是解锁路径的一半，另一半必须在硬件内 |
| "文件加密了就一定安全" | 加密与访问控制是两件事；进程一旦被授权读取，透明解密会替它完成工作 |

## 3. 隔离域与执行层的分工

### 3.1 为什么这一章要"极简重写"

本仓库已有关于 SPTM/TXM/Exclaves 的专门报告。此处不再复述其内部结构，只提取**安全语义**：iOS 的底层支撑里，"隔离"不是一个布尔量，而是一组彼此不可越权的执行域。防守方最需要掌握的，是如何用一句话说清每个域"守住了什么、守不住什么"。

### 3.2 机理：域的划分与职责

| 执行域 | 守住的性质 | 守不住的 | 语义标签 |
|--------|-----------|---------|---------|
| SEP / 安全协处理器 | 密钥不出边界、生物特征匹配判定、部分特权计时与策略 | 主处理器内存内容、应用层数据滥用 | G0 域 |
| 页表监视层（SPTM 一类） | 谁可以修改页表映射；把"映射权"从内核手里分出去 | 已经合法持有映射的代码的语义行为 | G1 域 |
| 执行监视层（TXM 一类） | 内核代码的合法性与策略决定 | 数据面漏洞（读原语、越界写仍在被允许的空间内） | G1 域 |
| 特权隔离执行环境（exclaves 一类） | 特定算法与关键运算在短生命周期隔离环境中完成 | 调用方传入数据的真实性 | G1 域 |
| 应用进程（EL0 + 沙盒 + 签名） | 进程间数据默认不可见、能力受权限系统约束 | 实现缺陷导致的原语泄露 | G3 域 |

这张表的关键结论是：**较新的 iOS 上，"控制面"（谁能改页表、谁能加载内核代码）被搬到了内核之外**。这解释了为什么公开研究里内核利用的重心从"任意代码执行"转向"信息原语 + 数据面操作 + 权限误用"。

### 3.3 保证：控制面强化的真实收益

- 让"改页表 → 映射任意物理内存 → 读 SEP 邮箱/绕过保护"这类经典内核手法失去立足点。
- 让内核代码的加载必须经过独立策略层批准，使"签名即信任"变成"签名 + 策略允许"。
- 使崩溃/异常后的部分关键决策不被被控代码左右。

### 3.4 边界：三个必须写清楚的限制

1. **域划分不自动修复越界读写**。在允许的地址空间内，一次越界写仍然是可利用原语；隔离层管的是"你能不能获得新能力"，不是"你的代码有没有内存安全"。
2. **豁免者真实存在且合法**。系统组件、开发者通路、恢复流程拥有普通进程没有的能力；"某个组件有特权"是设计的一部分，不是绕过证据。防守要问的是：这个特权组件的输入校验是否配得上它的权力。
3. **机型覆盖不齐**。这些机制依赖特定世代的 SoC 与系统版本。老设备上"同一份代码 + 较弱隔离"是常态；做产品安全评估时必须区分"文档上有"与"目标机型上有"。

### 3.5 观测：如何在现场判断隔离层是否在位

- **版本与机型基线**：先确定设备世代与系统版本，再对照官方平台安全文档判断该组合是否声明了相应机制。
- **锁定模式的语义作用**：启用锁定模式会收缩高攻击面服务与解释器相关能力，这是普通用户唯一能主动改变的"域边界配置"。它不改变硬件域划分，但显著改变暴露的服务集合。
- **异常表征**：系统在内存压力下的一致性失败、异常重启、内核 panic 日志中出现与页表/信任层相关的断言，通常是"控制面被触碰"的强信号。应急响应中，这类日志价值高于一般崩溃报告。
- **对开发者**：不要试图在第三方产品里"验证隔离层强度"；正确做法是确保自己的组件不假设可以从内核态获取任意内存访问，并在文档中声明所需权限的最小集合。

### 3.6 一句话总结

> iOS 底层支撑在"执行域"上的最大变化，是把**权力**（谁能改内存映射、谁能加载代码）从**知识**（谁能读懂内核）里剥了出来。防守方的对应变化是：审计重点从"这段代码是否被签名"转向"这个权力由谁持有、它的输入是否被校验"。

## 4. 代码完整性执行链

### 4.1 机理：签名不是单点检查，而是一条链

代码完整性在 iOS 上由多个 cooperating 层实现，每层的检查点不同，失败时机也不同。把它们当作"一个签名开关"会直接导致错误的威胁建模。

| 环节 | 作用点 | 检查内容 | 失败表现 |
|------|--------|---------|---------|
| 镜像加载（exec/mmap） | 内核 + AMFI | Mach-O 结构、代码签名（cdhash）、Team ID、必需 entitlement 是否被授权 | 进程无法启动，`Killed: 9` 类终止 |
| 页级校验 | 内核（与页表监视层协作） | 每个代码页与签名的哈希一致性 | 运行中页失效 → 进程被终止 |
| 动态链接校验 | dyld + library validation | 允许加载哪些外部代码（同 Team ID / 同签名策略） | `dlopen` 被拒 |
| 能力授予 | entitlement 检查 | 请求的特殊能力是否有对应签发授权 | 具体 API 返回失败或进程被拒 |
| 开发者/企业分发通路 | 安装与描述文件层 | 描述文件、证书有效性、设备注册 | 安装失败或到期后无法启动 |

关键语义：**iOS 上"能运行"意味着上述全部环节同时通过，而"曾经通过"不代表"现在仍被允许"**。证书吊销、描述文件过期、Team ID 变更都可能在运行期改变结果。

### 4.2 机理：entitlement 的三问

任何底层能力审计都可以压缩成三个问题，这是本报告在这一章想留下的可复用工具：

1. **谁签发？** entitlement 必须由匹配的申请方身份（签名、Team ID）签发，且签发通路（描述文件、MDM 策略、App Store 审核）在合法集合内。
2. **谁消费？** 拥有特殊 entitlement 的进程是攻击面：它必须校验所有外部输入的来源与语义。"有权力"与"被信任输入"之间的错配，是 iOS 特权组件漏洞最常见的结构性成因。
3. **能否传递？** 能力不应能经由子进程、XPC 调用、文件属性被间接转授。历史上一类反复出现的缺陷类别，正是"特权进程的辅助方法被低权限方调用，等效于转授权"。

### 4.3 机理：动态代码的三种合法形态与两种被削弱的检查

底层支撑允许加载外部代码的合法形态有限：系统框架、同一分发的扩展、被签名的动态库、JIT 生成的代码。相关策略原语：

- **库校验（library validation）**：默认只允许加载同 Team ID（或 Apple 签名）的外部代码。
- **允许无符号可执行内存**：为解释器/JIT 存在的豁免项。它的语义是把"页级签名校验"在该进程内关闭，代价是进程内的内存安全缺陷直接变成可执行原语。
- **允许调试 / 允许未签名可执行内存**类豁免：在开发版与企业分发场景存在，属于必须盘点的项目。

安全结论不是"这些豁免危险"，而是：**豁免项是设计者写给攻击面的一本说明书**。审计第三方 App 时，把这些豁免项列出来，基本就得到了它最脆弱的边界清单。

### 4.4 保证与边界

| 性质 | 强度 | 说明 |
|------|------|------|
| 未签名代码无法常驻运行 | G1 | 豁免者是持有特权能力的系统与开发者通路 |
| 代码页运行期不可篡改 | G1 | 与执行域协作实现；页失效即终止 |
| 跨团队代码注入受限 | G2 | 依赖库校验未被显式关闭 |
| 能力不可随意转授 | G3 | 依赖每个特权组件自行校验调用者，历史上反复失守处 |

边界要点：

- **签名验证的是"这段代码是谁写的"，不是"这段代码是安全的"**。大量恶意软件案例说明：签名完好 + 授权过度 + 实现缺陷，三者叠加即可造成真实危害。
- **开发者模式打开时，本机对签名与调试通路的约束被有意放宽**。这是用户主动选择，防守方必须能识别（第 13 章、第 19 章）。
- **越狱/篡改设备改变了执行链的假设**，但现代 iOS 上"部分绕过"与"完全接管"之间差距很大：即便执行链被削弱，数据保护与隔离域仍在别处守着自己的边界。因此检测越狱只应作为风险信号之一，而非唯一判据。

### 4.5 观测：如何盘点签名与能力边界

- **开发者侧**：发布前用签名工具导出 entitlement 清单，比对最小必要集；确认没有为了兼容而留下的"允许无符号可执行内存""允许调试""关闭库校验"类项目；把每一项残留写成书面豁免理由。
- **企业/管理侧**：通过 MDM 可查询已安装应用的签名身份与来源；重点盘查企业证书签发的应用（数量、有效期、是否仍在用）。历史上企业证书被盗用是最主要的可信分发失效方式。
- **应急响应侧**：对可疑设备优先确认三件事：开发者模式状态、描述文件清单、非 App Store 来源应用的签名身份。这三项能解释大多数"看起来像被植入"的现象。
- **取证侧**：崩溃报告与统一日志会保留签名失败/权限被拒事件，这类"失败记录"是判断系统防线当时确实在生效的正面证据。

## 5. 内存布局、随机化与分配器防线

### 5.1 机理：底层支撑提供了哪几种内存安全原语

iOS 的内存缓解措施可以按"它消灭的是哪一步"归类，这比按 API 罗列更有用：

| 原语 | 消灭的攻击步骤 | 强度 | 何时被削弱 |
|------|---------------|------|-----------|
| ASLR（代码/堆/栈/共享缓存） | 硬编码地址复用 | G2 | 信息泄露可重建布局；老设备熵较低 |
| 指针认证（PAC / BTI 类） | 直接控制返回地址、猜测合法目标 | G2→G1（视机型/系统） | 合法调用链被滥用（"借用"合法指针） |
| 页级签名校验 | 注入自有代码 | G1 | 拥有无符号可执行内存豁免的进程 |
| W^X / JIT 受控 | 数据变代码 | G1 | 解释器进程本身即例外 |
| 分配器加固（region 隔离、双 freed 检查、元数据保护） | 一次越界写即得任意写 | G2 | 分配器语义被"复用+竞争"绕过 |
| Guard page / guarded memory | 线性越界跨越 | G2 | 相邻分配、部分映射复用 |
| Tagged pointer / NaN-boxing | 指针低 bits 泄露直接可用 | G2 | 需与其他原语配合 |
| 内存完整性标记类机制（较新机型逐步引入） | 越界写本身 | 演进中 | 覆盖范围按版本扩大，不可假设全量 |

这张表的读法：**G2 行的价值在于"必须组合失效才可被利用"**。攻击链通常不"破解"某一项，而是让两项各自的部分弱点叠加：一次有限读原语抵消 ASLR 的价值，一次有限写原语抵消分配器加固的价值。

### 5.2 机理：共享缓存与镜像布局为什么关键

iOS 大量系统代码位于共享缓存（dyld shared cache）中。这对安全语义有两个影响：

1. **随机化单位变粗**：系统代码整体在地址空间中作为一个被滑动的对象，一旦其基址泄露，大量 gadget/函数入口同时可用。
2. **闭包与预链接改变了加载路径**：较新系统中 dyld 使用预构建的加载闭包，收益是启动性能与一致性，语义上是"加载决策前移"。对防守方的含义是：运行期通过环境变量或文件劫持加载过程的古典手法在 iOS 上基本不适用，因为根本没有那条通路。

### 5.3 机理：栈与调用的保护组合

调用栈保护在 iOS 上是组合式的：栈金丝雀、指针认证、异常处理路径受控。真正需要理解的是**为什么单看栈金丝雀会误判**：

- 金丝雀抵御"直接线性覆盖返回地址"。
- 它不抵御"对象虚表/块结构被改写后通过间接调用跳转"。
- 指针认证抵御间接调用目标被任意改写，但**不禁止使用一个合法的、被签名的指针**——这正是公开研究里 PAC 相关绕过的主流形态：不是"破解"，而是"借用"。

### 5.4 保证与边界

- **保证**：在启用了完整组合的系统/机型上，"单个内存安全缺陷直接得到完整控制流劫持"的成本被抬到很高；多数真实利用链需要多个原语拼接，这本身就是防御收益（也意味着检测面更宽，见第 9、19 章）。
- **边界**：
  - 任何持有 JIT 豁免的进程，其内存内"数据→代码"这一步是设计上允许的；对该进程的缺陷，缓解措施少一层。
  - 内核侧的分配器与用户态不同源，加固语义不能类推；内核利用相关细节在本仓库另有专题，本报告不重复也不给出方法。
  - 缓解强度与机型世代相关；对需要覆盖老设备的组织，安全评估必须按"最弱目标机型"做，而不是按最新发布机型。

### 5.5 观测：可行的观测点

- **对开发者**：使用系统提供的诊断能力（地址随机化状态查询、分配器调试选项）在测试机上确认自身产品的假设；不要在生产配置里开启任何调试型内存选项。
- **对安全审计**：把"目标进程是否有 JIT/无符号可执行内存/调试豁免"作为第一份清单；这是可远程判断（通过 entitlement）的高价值信号。
- **对应急响应**：崩溃报告里的终止原因非常有信息量——签名相关终止、页失效、PAC 失败（带特定异常代码）、金丝雀失败、分配器断言，各自指向不同的失效类别；把它们按类型统计，可以看出设备遭遇的是"恶意软件级"还是"利用链级"问题。
- **对普通用户**：可观测性有限，能做的最有价值的事是保持系统更新（缓解措施覆盖面随版本扩大）与谨慎对待需要"允许无限制访问"的组件。

## 6. Mach 内核对象与权柄语义

### 6.1 机理：为什么"权柄"是 iOS 权限模型的最小单位

Unix 传统里，进程间访问控制的核心是 UID/GID。iOS 的内核对象模型（Mach 的任务、线程、端口；IOSurface、命名空间等）在此之上引入了另一层：**能力句柄（right）**。持有某个端口的发送权，就拥有向该对象投递消息的能力；这个能力不体现在文件权限里，也不体现在 UID 里。

安全语义上的推论很重要：**"我能连上这个服务"不等于"这个服务认为我是谁"**。iOS 上大量权限判断依赖内核提供的调用者身份（audit token），而不是网络/地址层面的表象。

### 6.2 机理：audit token 与身份传递

内核在跨进程交互时携带调用方的审计凭据，用户可以从中解出 PID、UID、GID、代码签名要求等。这个凭据是 iOS 授权体系里最重要的一次"实现纪律考验"：

- 服务端**必须**主动校验它。
- 校验对象应当包含身份（谁在调用）与授权（它被允许做什么）两件事；只校验其一，历史上都产生过真实缺陷。
- 凭据不可由调用方伪造（这是内核保证），**但可以被"忘记检查"**——这是 G3 层失败，而不是原语失效。

这一区分是本章核心：**iOS 提供了难以伪造的身份，但没有强制使用它**。底层支撑里凡是"提供了但可选择不用"的原语，都应进入审计清单的顶部。

### 6.3 机理：特权端口与调试能力

系统中存在若干高价值端口/句柄（任务端口、调试端口、主机特殊端口一类）。它们的语义是"持有即拥有观察或控制该任务的能力"。底层支撑的历史演进方向非常一致：**逐步收窄获取路径**。

- 获取他任务端口的能力被限定给极少数持有专用权限的组件（典型是系统调试与分析通路）。
- 沙盒策略默认拒绝跨任务的敏感句柄操作。
- 较新系统上，与调试相关的合法通路被迁移到显式的开发者/诊断流程（第 13 章），而不是隐式的端口访问。

防守含义：**任何仍在提供"按 PID 换取任务句柄"能力的组件，都是本机上被绕过隔离的候选点**。这类组件通常存在合理理由（性能分析、崩溃采集 SDK），审计时应要求它具备白名单与调用者校验，而不是仅要求权限存在。

### 6.4 边界与失败模式分类

| 失败模式 | 描述 | 层级 |
|---------|------|------|
| 身份未校验 | 服务端信任任何能连上的调用者 | G3 |
| 身份校验但不校验授权 | 承认"谁在调用"，但对所有调用者提供同一功能集合 | G3 |
| 能力代理（confused deputy） | 特权组件被低权方调用去完成自己不敢做的事 | G3，最常见 |
| 句柄意外可达 | 端口被继承/传递到不该持有的域 | G3/G1 交界 |
| 句柄获取通路过宽 | 特定调试/分析通路未按调用者收紧 | G1 |

值得注意的是：这些失败模式**都不需要突破签名、不需要内核漏洞**。这是"底层支撑的安全语义"章节里最应该被非专业读者理解的一点：真实世界里大量提权发生在权柄与授权层，而不是在页表与加密层。

### 6.5 观测

- **对开发者**：为自有 XPC/服务定义调用者白名单，并把"未通过校验即拒绝且记录"作为默认实现；测试时用非预期调用者验证拒绝路径真的被走到。
- **对审计/取证**：设备备份/取证包中的系统日志可显示访问被拒绝的授权事件；对特权组件的清单盘点（谁在运行、什么身份、暴露哪些服务）比追踪单个调用更可执行。
- **对应急响应**：可疑进程持有异常能力句柄，通常需要特权上下文才能观察到；普通用户可做的最有价值判断是"这个进程为何存在"（第 14、19 章的持久化与来源清单）。

## 7. 进程间通信的授权语义

### 7.1 机理：三代 IPC 与各自的检查点

iOS 底层支撑里的 IPC 大致分三代，安全语义各不相同：

| 机制 | 定位 | 授权语义 | 典型失误 |
|------|------|---------|---------|
| Mach 消息 | 内核原语 | 持有发送权即可投递；身份靠 audit token | 假设"能连上即可信" |
| XPC（C API） | 系统服务主干 | 对端身份可由连接对象取得；需服务端主动校验 | 忘记取用对端凭据 |
| NSXPC（Objective-C） | 面向对象的远端调用 | 自动序列化 + 代理模式，**不默认校验调用者** | 把远端方法当作本地私有方法暴露 |

NSXPC 是三者中语义风险最高的：它把远程调用包装得像本地方法，容易让实现者忘记"每一次方法调用都可能来自不受信任进程，而且参数是任意对象"。

### 7.2 机理：解档即执行——跨进程边界的数据陷阱

跨进程传递对象需要反序列化。底层支撑提供 secure coding 类约束，但语义上要理解：**反序列化是一个代码执行入口**。

- 若接口接受通用对象类型，等价于暴露"对端可构造任意被支持类型"的能力。
- 历史缺陷类别里有一类反复出现：解档路径触发非预期的类初始化副作用，从而在低权限方手上得到一次高权限进程内的代码执行机会。
- 正确的表达方式是"接口只接受明确白名单类型 + 显式 schema + 参数范围校验"。

这就是典型的 **G3 原语**：系统给了解法，不强制使用。

### 7.3 机理：沙盒与授权在 IPC 上的交汇点

一次跨进程调用的实际检查结果，是三层策略的交集：

```
沙盒配置文件（能不能连这个 endpoint）
  ∩ entitlement / 能力（能不能请求这个特权服务）
    ∩ 服务端自定策略（我认不认识你）
```

三层由不同主体编写：Apple 与开发者写沙盒与 entitlement，第三方写服务端策略。防守方的现实问题因此是：**前两层你无法审计（在系统内），第三层完全依赖被审对象自觉**。安全评估时，应把第三层当作唯一可影响的对象，并对所有跨进程入口做输入契约化。

### 7.4 边界与已知风险面

- **系统守护进程数量庞大**：iOS 上长期运行的 XPC 服务数以百计，每个都是攻击者的候选输入点；底层支撑不可能为它们统一编写策略，这正是提权研究的主要矿区。
- **第三方扩展进程**：App Extension、网络扩展、文件提供程序运行在不同沙盒里，与主应用共享数据容器；跨边界的信任假设常常写成"这是我自己的进程"，而真实边界由系统强制执行。
- **推送与后台唤醒通路**：由系统投递，触发进程后代码路径可能被外部数据影响；语义上它属于"外部可达入口"，即使没有监听端口。
- **HID/USB 类近场通路**：属于第 14 章，但它的授权语义同样是"连接即能力"，需要独立策略。

### 7.5 观测

- **开发者**：把"所有 XPC 入口都实现了调用者校验吗"作为发布前的固定检查项，并在接口注释里写明校验类型；对每个远端接口做一层"非白名单调用者必须失败"的测试。
- **审计**：设备侧可枚举可见的服务标识与 mach 服务名（在具备读取能力的分析环境中），与已知的合法组件清单比对；出现无法解释的新服务名是强信号。
- **应急响应**：优先看"未授权访问被拒"类日志的突增；攻击者在探测服务时的失败记录，往往早于成功利用。

## 8. 沙盒配置与三层授权的叠加方式

### 8.1 机理：沙盒是策略语言，不是目录约定

iOS 的应用沙盒常被误解为"数据放在自己的容器里所以安全"。真实的底层语义是：内核与系统框架在关键路径上执行一份**策略描述**（sandbox profile），决定"这个进程能否打开这个路径、连这个服务、发这个消息、访问这个硬件"。容器目录只是策略默认允许的区域之一。

这带来三个防守方必须内化的语义：

1. **默认拒绝 + 显式例外**是策略意图；例外越具体，防线越清晰。
2. 策略与 entitlement **相互独立**：拥有 entitlement 但沙盒不放行，仍然失败；反之亦然。
3. 策略的**表达能力即攻击面**：任何"允许写入某目录 + 该目录被特权进程读取"的组合，等价于一条间接提权路径。

### 8.2 机理：权限体系的四层，谁管什么

```
能力层：entitlement（你能不能被授予这个特权）
策略层：sandbox profile（进程能触碰哪些资源）
授权层：TCC / 用户同意（是否允许访问个人数据类别）
保护类层：数据保护（密钥在该状态下是否可用）
```

四层是乘性关系：**任何一层通过都不等于整体允许**。真实产品里最常见的错误是只讨论授权层（弹权限框），默认其余三层与它同义。

对隐私的意义尤其重要：一个进程可能"沙盒允许、entitlement 允许、用户也给了权限"，但若数据处于"解锁后才可用"的保护类，未解锁时读取仍然失败。反过来说，防守方不能因为"有 TCC 弹窗"就认为访问被控制住了——TCC 只覆盖个人数据类别，不覆盖设备内的其他资源。

### 8.3 机理：共享区域与策略交界

iOS 上真正的风险集中在"多方可触达"的交界：共享容器（App Group）、可被用户导入导出的文件、下载目录、照片选择通路、文件提供程序、通过 URL scheme/通用链接进入的解析路径。

安全语义要点：

- **共享容器内不再有沙盒级细分**：同一 group 内所有成员可读写全部数据。把敏感密钥放进共享容器等于放弃单应用边界。
- **跨边界传递文件时，元数据与扩展属性的处理是策略的一部分**：隔离标记（quarantine 类属性）在 iOS 上主要服务于来源可信判断，不应把它当作"内容安全检查"。
- **文件协调/冲突处理机制带来 TOCTOU 窗口**：检查与使用之间的时间差是经典 G3 缺陷，尤其在"先判断类型再打开"的实现里。

### 8.4 保证与边界

| 性质 | 强度 | 边界 |
|------|------|------|
| 应用无法随意读取他人容器 | G1 | 豁免者是持有系统级文件能力的组件；备份通路另算 |
| 敏感硬件访问需运行时授权 | G1 | 依赖实现方在正确位置执行检查 |
| 沙盒限制逃逸后的活动半径 | G2 | 逃逸本身即意味着已进入被允许的区域 |
| 扩展进程受独立策略约束 | G1 | 扩展与主应用共享数据，边界不是隔离 |

最需要强调的边界是：**沙盒不防御"合法权限的滥用"**。一个拿到相册写入权限的应用，其全部行为都在策略内；这类风险只能由隐私政策、审核与最小权限实践约束，底层技术不承担该责任。

### 8.5 观测

- **开发者**：把自家 profile/entitlement 需求写成文档化清单；每次新增例外都需要一条明确的功能理由；避免"为了方便调试"扩大目录权限。
- **管理侧**：MDM 可以限制部分能力与安装来源；审计重点是"哪些设备处于放宽状态（开发者模式、未受管安装）"。
- **取证侧**：容器结构与策略语义决定了备份里能看到什么。理解"备份覆盖哪些容器、哪些类别受保护类限制"，比理解文件系统本身更实用。

## 9. 异常、崩溃与诊断通路

### 9.1 机理：两套异常体系并存

iOS 同时存在两套语义不同的异常处理体系，防守方需要能区分它们的产物：

- **Mach 异常**：内核向"异常端口持有者"发送消息，由用户态崩溃处理组件接管，产出结构化崩溃报告。它覆盖非法内存访问、指令异常、代码签名相关终止。
- **BSD 信号**：POSIX 层的信号语义，主要用于可恢复错误与终止通知，也是部分库内部错误处理的通道。

崩溃报告的产出通路在系统演进中发生过迁移（较新的系统由新的诊断报告体系接管，替代旧式 crash reporter 的角色）。语义上不变的是：**崩溃报告是最早、最结构化、且用户可控可见的本地攻击痕迹**。

### 9.2 机理：终止原因承载安全信息

从防御角度看，崩溃报告的"终止原因/异常代码"字段是分类工具：

| 终止类别 | 语义 | 处置含义 |
|---------|------|---------|
| 段错误 / 非法地址 | 内存安全缺陷 | 单个应用自身质量问题；量大时值得怀疑 |
| 代码签名/页失效类终止 | 完整性检查触发 | 强信号：有人在动可执行代码 |
| 指针认证失败类终止 | 控制流被篡改的尝试 | 强信号，值得立刻响应 |
| 分配器/元数据断言 | 堆破坏 | 中强信号 |
| Jetsam（内存压力终止） | 资源治理 | 通常非攻击，但异常密集可指示内存驻留行为 |
| 看门狗/无响应终止 | 主线程卡死 | 多为质量问题 |

关键结论：**当缓解措施真的起作用时，它会留下可计数的痕迹**。这正是"观测"维度最实的一章——缓解措施不是不可见的承诺，而是每次失败都写下一条记录。

### 9.3 机理：统一日志与 os_log 的隐私语义

系统日志（统一日志体系）是底层支撑里最重要的可观测性基础设施，也是**攻击者想关掉的东西**。它的两个安全语义常被忽略：

1. **默认脱敏**：日志点可以把数据标记为隐私参数，输出时被替换为占位内容。这不是运行时权限，而是**编译期决定**——因此"日志里没泄露"依赖开发者是否用对了参数类型，属于 G3。
2. **落盘与持久化级别可被调整**：某些类别的日志默认不持久化；把类别提升到持久级别会改变可取证的时间窗口。攻击者会试图压低日志级别，防守方应把"日志强度是否被异常配置"视为信号。

### 9.4 机理：系统诊断采集（sysdiagnose 一类）的取证价值

一键触发的诊断采集会打包大量底层状态：进程与内核日志、网络与蓝牙状态、电源与存储信息、崩溃历史。对防守方它是**最可靠的现场快照**；对高价值目标它同时是一个隐私披露面——因为它包含的内容远超普通日志。

安全语义：

- 采集需要物理操作触发（按键组合），因此它天然是"设备持有者可自愿提供"的证据通路。
- 采集产物中"底层保证是否生效"的证据密度极高（重启历史、异常终止、策略拒绝记录），应急响应应默认在设备仍在手上时先做一次采集。
- 采集内容可能包含敏感标识与连接历史，交付第三方前需要按泄露风险评估处理。

### 9.5 边界

- **崩溃记录不完整**：被更高层机制直接终止的进程，可能不产出用户可见报告；内核 panic 后需要重启才可在存储中读到记录。
- **保留窗口有限**：日志与崩溃文件按容量与时间轮转。"没找到证据"不等于"没有发生"。这一点在事件响应中必须写进结论表述。
- **备份覆盖差异**：本地备份、iCloud 备份、ADP 状态下可见内容不同，取证可用性依赖备份时机与类型。
- **锁定模式的影响**：启用后部分诊断/连接通路被收紧，这会降低远程观测能力，同时也降低被远程观察的面。

### 9.6 观测：分类与统计流程（防御侧）

推荐把崩溃与日志当作指标而不是个案：

1. 按终止类别做时间分布（关注签名类、PAC 类、堆断言类的突增）。
2. 按进程维度看"陌生进程"（名称、签名身份、启动来源）。
3. 关注"本不该出现"的异常组合：系统守护进程崩溃、同一进程反复被完整性机制终止、恢复后仍持续出现。
4. 与已知恶意软件行为特征比对（持久化位置、外联时间规律），而不是与漏洞利用特征比对——后者通常不需要防守方自行识别。

## 10. 时钟、随机数与确定性服务

### 10.1 机理：为什么把时钟与随机数列为"底层支撑"

大多数安全讨论把这两项当作库问题，但它们在 iOS 上是由内核与安全协处理器提供的**基础服务**，且具有明确的攻防语义。

- **单调与墙钟双轨**：系统同时维护单调时间（用于调度、超时、性能测量，不受设置改变影响）与墙钟时间（可被用户或网络校时改变）。安全语义是：**任何有效期、重放防护、速率限制都必须建立在单调时间上**，否则用户改一次系统时间就能改变策略结果。
- **特权限制**：非特权进程无法任意设置系统时间；时间同步走受控通路。这使得"改时间绕过证书有效期"在 iOS 上比在桌面系统上更受限——但仍要求应用不能以本地时间为唯一判据。

### 10.2 机理：随机数来自哪里

底层支撑的随机数供给是分层：

```
硬件熵源（SoC 随机数发生器、传感器抖动等）
    └── 内核 CSPRNG（维护状态、按请求输出）
            └── 系统 API（SecRandomCopyBytes 一类）
    └── SEP 内部随机数（用于密钥生成路径）
```

安全语义要点：

1. **默认路径正确但可被绕开**：系统提供了明确的、以 CSPRNG 为后端的接口；风险来自开发者为了"可复现"或"方便"使用可预测种子（时间戳）自行生成标识或令牌。这是纯 G3 失败。
2. **标识符的随机化也是一种底层支撑**：隐私相关的不追踪标识、蓝牙/Wi‑Fi 地址策略、启动参数随机化，共享同一原则——"稳定标识是可关联的秘密"。
3. **密钥生成的正确通路包含硬件参与**：涉及长期密钥的场景应由系统密钥设施生成与保管，而不是应用自己生成后落盘。

### 10.3 攻防：确定性与时间的攻击面

| 场景 | 依赖的底层性质 | 防守要点 |
|------|---------------|---------|
| 证书/令牌有效期校验 | 墙钟 + 单调时钟一致性 | 关键决策不要只信本地时间；对时间跳变有检测 |
| 重放攻击防护 | 单调序号 + 新鲜性 | 用系统提供的安全存储保存计数器，不要写普通文件 |
| 速率限制与爆破防护 | 单调计时、失败状态持久化 | 状态需要跨重启保留，且处于受保护类 |
| 令牌/标识可预测性 | CSPRNG 使用正确性 | 审计所有自行生成标识的代码路径 |
| 定时任务与自动化的隐私 | 精确计时能力 | 时间规律本身可泄露行为模式（本报告系列另有专题） |

### 10.4 侧信道与确定性服务的边界

底层支撑的确定性还有另一面：性能优化通路（缓存、预取、分支预测、压缩）会引入可观测的时间差异。公开研究已经就 Apple Silicon 上的若干微架构侧信道给出分析（涉及特定加密运算路径的可观测性）。防守结论务实：

- 不要把机密数据放进可能被同机不可信代码共同影响的执行路径。
- 高价值长期密钥应由系统密钥设施与安全协处理器保管，不在应用内自行拼装运算。
- 对"跨进程缓存侧信道"，用户层面唯一有效的缓解是减少不可信代码并发运行（不安装来源不明的东西），这与本报告系列的通用结论一致。

### 10.5 观测

- **对开发者**：在测试中主动改变系统时间，验证自家策略不因墙钟跳变而失效；用固定策略生成密钥与标识（禁止手写随机数）。
- **对审计**：检查应用是否持久化了"看起来随机但其实稳定"的设备标识；检查是否使用可访问级别过弱的存储保存计数器与密钥。
- **对应急响应**：系统时间被异常改动、时区与校时来源不一致，常是攻击者尝试延长令牌有效期或规避校验留下的痕迹；这一项应在事件响应早期确认。

## 11. 文件系统底层与数据完整性

### 11.1 机理：现代文件系统与数据保护是两个正交层

iOS 使用现代写时复制文件系统（APFS 家族），提供快照、克隆、空间共享等能力；同时数据保护通过加密引擎与密钥层级在**文件内容/元数据**层面提供机密性。两者语义不可混淆：

| 能力 | 提供什么 | 不提供什么 |
|------|---------|-----------|
| 写时复制 + 事务 | 崩溃一致性（结构不被破坏） | 内容未被篡改的证明（不对外提供可验证的完整性证明链） |
| 快照 | 历史版本、恢复点 | 防篡改；快照可被删除/覆盖 |
| 克隆 | 空间高效复制、共享数据快速实例化 | 权限隔离；克隆后仍受同样的数据保护与沙盒约束 |
| 数据保护类 | 特定状态下密钥不可用 → 内容不可读 | 访问控制；已授权进程读取时自动解密 |
| 只读系统卷的签名校验（较新系统） | 系统内容完整性可验证 | 用户数据区的同等保证 |

需要明确写出的一条边界：**文件系统本身不给你"哪些文件被谁改过"的答案**。完整性判断只能来自签名验证、系统卷校验与外部时间线证据（日志、快照对比、备份比对）。

### 11.2 机理：扩展属性与元数据的策略含义

iOS 把若干策略信息编码在文件的扩展属性与元数据中：来源标记、隔离标记、快速索引、内容类型识别等。安全语义：

- 这些属性**参与决策**（例如来源可信判断），因此是攻击者会尝试清除的目标。
- 它们不是内容检查；"清掉标记"可能改变策略结果而不改变字节。
- 应用不应依赖扩展属性做安全判断，尤其不应把敏感信息写进去（部分属性在跨应用传递、备份与共享时可能不被保留，甚至泄露实现细节）。

### 11.3 机理：路径、链接与挂载边界

内核层的路径解析（符号链接、硬链接、大小写与 Unicode 归一、挂载点遍历）是历史上跨平台提权缺陷的高产区。iOS 的语义约束主要来自沙盒与容器结构，而不是路径本身的防御性设计。防守要点：

- **"检查后使用"（TOCTOU）在容器共享目录中依然成立**；跨边界文件处理要用原子操作或系统提供的协调机制，并重新校验。
- **大小写与归一化差异**在跨系统交换（Mac/Windows/服务端）时可能导致策略绕过：沙盒按实际路径判定，攻击者可能构造视觉上等价、判定上不同的名字。
- **归档解包（zip 类）必须做路径约束**：这是应用层最常见的"底层特性被误用"缺陷类别之一。

### 11.4 机理：备份通路是文件系统语义的一部分

备份（本地加密备份、iCloud 备份）不是"文件系统之外的事"，它决定了：哪些容器被复制、哪些数据以何种保护级别离开设备、以及取证人员能看到什么。

- 备份加密强度依赖用户是否设置额外口令；否则备份内容可能对备份创建者一侧可解。
- 端到端保护的类别（钥匙串、健康、部分 iCloud 数据）与备份可见性之间存在配置耦合；高级数据保护的开关会改变备份中敏感内容的形态。
- 备份是"时间机器"：它保存了历史状态，这对防守与取证是收益，对被遗忘权与泄露控制是负担。

### 11.5 观测

- **开发者**：审计三类路径——解包入口、文件共享入口、跨容器写入；对每处确认"重新校验 + 原子替换 + 不依赖扩展属性做安全判断"。
- **管理侧/取证侧**：把"备份时间点"作为完整性基线。做变更检测时最可行的办法是"两个时间点快照比对"，而不是指望文件系统提供篡改证明。
- **用户侧**：能做的最有价值两件事：保持系统更新（文件系统与数据保护的实现缺陷修复随版本走），以及对备份口令与端到端保护设置做出明确选择，而不是默认。

## 12. 引导、恢复与升级通路

### 12.1 机理：三条独立的验证通路

iOS 底层支撑在"如何进入可信状态、如何变更状态"上提供三条彼此独立的通路，混用它们的概念会造成大量错误讨论：

| 通路 | 目标 | 验证核心 | 安全语义 |
|------|------|---------|---------|
| 启动链 | 从不可信上电状态到内核运行 | 逐级签名验证 + 一次性/版本相关授权信息（APTicket 类） | 决定"这台设备现在跑的代码是谁的" |
| 恢复/刷机 | 替换系统映像 | 映像签名 + 个性化授权（服务器参与） | 决定"允许安装什么版本" |
| 增量升级与安全响应 | 更新部分组件 | 组件签名 + 可回滚策略 | 决定"多久能修好一个漏洞" |

其中"降级防线"（anti-rollback）的语义值得单独说清楚：它约束的是**可安装版本集合**（服务器只签发当前允许的构建授权），从而防止用户被动回到含已知漏洞的版本。它**不是**数据密钥的一部分，也不影响设备上已有数据可读性；把两者混为一谈是常见的误判。

### 12.2 机理：升级通路带来的新原语——部分更新

现代 iOS 引入了"快速安全响应"式机制：以小而可独立验证的组件形式尽快下发安全修复，用户可以延迟重启而不影响主更新。底层语义变化很实在：

- 系统分区被拆成可独立签名的组成单元（cryptex 类），使"修一小块"不再需要整包更新。
- 收益：**缩短了最脆弱的窗口**（已知漏洞已修但尚未下发）。
- 代价与边界：**引入了"补丁已安装但未生效"的新状态**。防守方必须能区分"版本字符串"与"当前运行配置"，否则会误判加固进度；对高价值目标，这类组件的生效时间应与风险事件时间线对齐。

### 12.3 机理：协处理器与基带是独立更新对象

SEP、基带、若干外设固件拥有各自的签名与更新通路，不与主处理器代码同生命周期。安全语义要点：

- 主系统被更新，不代表协处理器/基带固件被更新；反之亦然。
- 这些组件通常是"用户完全不可见"的代码，且拥有较强的硬件访问能力；Apple 官方文档明确它们有独立的安全目标与设计约束（本仓库另有专题报告）。
- 对基带的暴露面管理（例如关闭不再需要的旧制式支持）是少数高价值目标可以做出的实质性选择，这与锁定模式提供的收紧项一致。

### 12.4 边界：恢复流程是"合法降级防线"的例外窗口

- 恢复模式下的操作需要设备进入特定状态并通常伴随数据擦除路径，这是设计上的风险收敛方式。
- 激活锁与"查找"机制属于**账户层的恢复通路约束**，它约束的是"设备重新激活需要原账户"，而不是加密强度。防守上应把它当作抗盗窃而非抗取证机制来描述，避免夸大。
- 企业环境中，MDM 与监管流程可能引入合法的托管恢复能力；这些能力应在资产清单里被显式记录，不能被当作"系统默认"。

### 12.5 观测

- **判断升级是否真正生效**：确认当前运行组件版本与"待重启生效项"状态（在具备权限的分析环境可读，普通用户可通过重启节奏与版本信息间接判断）。
- **恢复事件留痕**：设备是否近期被刷机，可通过备份/时间线证据、激活与账户提示、数据缺失模式（历史消息、日志断档）反推。应急响应中，"数据异常干净"本身就是信号。
- **基带/独立固件的可观测性很差**：对普通用户只能靠保持更新与来源管理；这也是本报告把固件面归类为"信任型防线"的原因。

## 13. 调试、剖析与开发者通路

### 13.1 机理：iOS 把"可调试性"变成了显式特权

这是 iOS 底层支撑与桌面系统最重要的语义差别之一。桌面传统上默认允许附加调试器与内核调试；iOS 则把它变成需要用户主动开启、且系统会持续提示的状态。

| 通路 | 语义 | 风险面 |
|------|------|-------|
| 开发者模式（较新系统引入） | 本机被允许运行开发签名代码并接受调试连接 | 开启即显著扩大可执行代码来源集合 |
| 设备配对与调试连接 | 主机获得观察设备的能力（进程、文件、日志） | 主机侧信任被继承到设备 |
| 诊断/分析采集 | 只读、大批量导出状态 | 隐私披露，而非提权 |
| 内核调试与低层剖析 | 仅面向受限工程场景 | 平台内部通路，普通环境不可用 |

底层剖析能力（例如动态跟踪类工具）在移动平台长期不可用或严重受限：这是**设计上的自我约束**——放弃一部分可诊断性，换取攻击者无法使用同一能力。防守方需要接受这个取舍的现实后果：现场可观测性不如桌面，很多结论只能靠日志、崩溃记录与备份推断。

### 13.2 机理：配对（trust relationship）是一种隐式能力授予

主机与设备建立配对关系后，可获得的访问范围远超"同步照片"的直觉。安全语义：**配对是一次信任扩张事件**，它把主机上的任何有权限进程可能获得的设备访问能力一并纳入攻击面。

防守要点：

- 陌生配对请求（尤其"你的设备信任了某台电脑"类提示）应视为安全事件而非操作提示。
- 不需要的配对应清除；公共/借用主机上的配对最容易被遗忘。
- 组织里"IT 用主机批量管理设备"的通路属于合法但需盘点的信任扩张。

### 13.3 机理：开发者通路与真实攻击的关系

历史上"开发签名 + 企业证书"是最常被滥用的可信分发通路：被盗用的企业证书可以让攻击者以合法签名分发恶意代码。底层语义是——**签名机制保证了"来自谁"，不保证"意图良善"**；因此吊销（证书撤销、OCSP 式检查）成为这条链上真正的防线。

对防守方的可操作结论：

- 关注"未过期、但已吊销"的签名应用；这类应用在安装或启动时会失败，失败历史是有价值信号。
- 企业分发应用数量应被管理侧监控，异常增长通常意味着管理漏洞。

### 13.4 观测：如何判断本机调试面是否被打开

普通用户可查的项：设置 → 隐私与安全性 → **开发者模式**状态；已配对主机清单（在设备管理界面）。分析/取证环境可进一步确认调试相关服务的存在与历史连接记录。

对高价值目标的加固语义：
- **不需要调试就关闭开发者模式**，并对开启状态设置变更提醒（若有 MDM 策略支持）。
- **把配对清单纳入例行审计**，如同审计已安装描述文件。
- 意识到"开发者模式已开"的设备，其完整性保证等级应从 G1 降级评估：此时"能运行的代码来自哪里"这个问题的答案被用户主动放宽了。

## 14. 外设固件与 DMA 边界

### 14.1 机理：外设是"有自己代码的部件"

iOS 底层支撑里最容易被忽略的一类，是拥有独立固件与较强硬件访问能力的外围处理器：无线基带、蓝牙/Wi‑Fi 组合芯片、电源管理单元、图形处理器、存储与 USB 控制相关部件。它们的共同安全语义是：

1. **有可更新代码**，且更新通路独立（第 12.3 节）。
2. **能通过 DMA 访问主内存**，这使它们成为"绕过 CPU 层保护"的潜在通路。
3. **对用户完全不可见**，因此防守只能依赖"信任 + 更新及时性"，而不是"检查与配置"。

### 14.2 机理：DMA 与内存管理单元的作用

现代 SoC 用 IOMMU 类机制（Apple 平台上通常以 SMMU 表述）限制外设可访问的物理地址范围。安全语义：

- 它把"设备固件被攻破"与"设备固件可直接读取全部内存"分开——前者不等于后者。
- 边界配置的粒度决定实际效果；对可插拔外设（Thunderbolt/USB4 类）尤其重要，因为物理插入本身就是能力授予事件。
- 在移动设备上这一面比桌面小得多，但并非零：近场无线与有线接入都在策略范围内。

### 14.3 机理：无线接入作为底层通路

蓝牙、Wi‑Fi、蜂窝、NFC 的接入决策由系统网络栈与内核共同完成（本报告系列另有无线安全专题）。此处只提取与"底层支撑"直接相关的语义：

- **自动连接与历史凭证**是"无需用户在场即可接受的连接"，这是最典型的信任扩张项。
- **无线芯片是独立代码实体**，其历史缺陷模式（无需配对即可触达的解析逻辑）使其具备零点击属性。
- 防守方可做的实质选择很有限，且都属于"关闭通路"而非"加固通路"：不需要的无线能力关掉、旧制式蜂窝支持在锁定模式下收紧、陌生环境关闭自动连接。

### 14.4 边界

- **物理侧信道与故障注入**属于硬件对抗范畴，超出本报告讨论；其结论只有一条防守意义：高价值目标的密钥保护不应假设"设备始终在自己手里"。
- **外设固件漏洞的可见性接近零**：用户无法知道自己是否处于"某个基带缺陷未修"状态，只能通过更新节奏间接管理。
- **配件供应链**：非认证配件与转接器引入的是输入侧风险（HID 注入类），本质是"把外部设备当作键盘"的信任假设。桌面与移动都受此影响，移动的边界更依赖"锁屏 + 配件策略"。

### 14.5 观测

- 可核实的观察：更新是否及时（唯一可控变量）、锁定模式是否收紧了无线与旧制式、组织侧是否限制了配件与连接策略。
- 应急响应侧：连接历史（Wi‑Fi/蓝牙配对清单）、异常时间点的射频状态、外设相关日志条目，是判断"近场通路是否被使用"的可用证据；这些内容通常出现在诊断采集包里。
- **不要试图用应用内检测判断固件是否被攻破**——这不现实；固件面属于"信任型防线"，把它放进风险接受清单而不是检测清单。

## 15. 对象运行时与动态派发的安全语义

### 15.1 机理：iOS 上有两套"运行时"，安全性质完全不同

底层支撑里最容易被子系统型文档一笔带过、却在攻防中权重很高的一层，是**对象运行时**。iOS 上并存两套语义差异很大的运行时：

| 运行时 | 派发方式 | 元数据可见性 | 安全语义 |
|--------|---------|-------------|---------|
| Objective-C 运行时 | 消息发送（按选择子动态查表） | 类、方法、协议列表在镜像中结构化可见 | 动态可改：类替换、方法交换、动态注入 |
| Swift 运行时 | 静态派发与函数签名表为主，泛型元数据与 ObjC 桥接处仍动态 | 元数据更紧凑但同样存在于镜像 | 可改面较小，但互操作边界继承了 ObjC 的开放性 |

核心语义是：**消息发送在运行期由数据（选择子字符串 + 类结构）决定，而这些数据本身位于同一进程可读写的内存里**。因此"能在目标进程里执行任意代码"与"能改变目标进程的行为"之间，运行时几乎不提供额外隔离。

这不是缺陷，而是明确接受的设计取舍——它换来了界面构建、键值编码、归档、动态库与兼容层。防守方要理解的是：**运行时的开放性使"进程内内存安全缺陷"的破坏上限被抬高**，而不是"iOS 多了一个漏洞"。

### 15.2 机理：三类合法的"改写行为"能力

底层支撑提供的合法动态能力同时是三类需要盘点的攻击面：

1. **方法交换（swizzling 一类）**：运行期替换某类某方法的实现，调试、埋点、兼容补丁都依赖它。语义上等于"就地改写调用图"，链条上的每一环都假定自己拥有全进程控制权。
2. **动态类注册**：运行期构造类并注入方法表，插件与桥接实现的常用手段。
3. **按名称访问（键值编码与路径类）**：用字符串访问属性。机制本身无害，风险在于**把外部可控字符串交给它**——那等价于开放"按名字探测内部结构"的能力。

审计要点集中在第 3 类：外部输入直接进入反射/路径解释接口，是应用层最常见的结构性错误之一。沙盒把其他路径收敛掉之后，这类入口反而更突出。

### 15.3 机理：代码注入为什么"进不去"

理解运行时安全语义的另一半，是搞清楚 iOS 在**进程边界**上把动态能力关在门外。桌面惯用手法在 iOS 上没有立足点，各有具体机制在守：

| 桌面惯用手法 | iOS 拦截点 | 对应原语 |
|-------------|-----------|---------|
| 把外部库塞进别人的进程 | 不开放注入路径 + 库校验限制可加载代码身份 | 第 4 章 |
| 调试器附加后注入 | 调试端口获取被限定给受控通路 | 第 6.3 节、第 13 章 |
| 用环境变量改变加载 | 加载决策由预构建闭包决定，无变量注入通路 | 第 5.2 节 |
| 改数据段函数指针后执行 | W^X + 页级签名校验：数据不可执行 | 第 5 章 |

于是 iOS 上"注入"的真实形态收敛为两种：**（a）先取得进程内执行能力，再用运行时的开放能力放大破坏力；（b）让目标进程自愿加载"合法身份"的代码或数据驱动逻辑**。第 (b) 类对防守方更重要，因为它不需要内存安全缺陷——只需要写入一个"目标会当行为解释"的位置。

> 这正是第 8.1 节"策略交界即攻击面"在运行时层的体现：沙盒允许写入 + 目标把该处内容当行为解释 = 等效代码注入。

### 15.4 机理：解档与反射必须白名单化

运行时把"数据→对象"做成通用能力，因此对它的信任要求必须是显式的：

- **解档**是运行时代码执行入口（见第 7.2 节），接口只应接受明确白名单类型与显式结构。
- **按键名反射**必须先做映射表（外部名→内部字段），不让外部字符串抵达反射层。
- **插件式类发现**要校验候选类的类型与来源，而不是"找到什么用什么"。

这三条是本章唯一需要写进代码规范的部分，检查项也最简洁：**外部输入是否直接进入了任何按名字解释的接口**。

### 15.5 保证与边界

| 性质 | 强度 | 说明 |
|------|------|------|
| 跨进程运行时劫持不可能 | G1 | 由签名执行链与库校验保证，而非运行时封装 |
| 进程内实现可被动态改写 | 设计开放（G3 依赖） | 一旦取得执行能力，运行时不再提供额外隔离 |
| 二进制接口信息可静态读出 | G2（可接受成本） | 类/方法/协议存在于镜像，是逆向入口而非漏洞 |
| 字符串驱动的反射安全 | G3 | 完全取决于是否做了名字映射 |

边界要说透：**运行时不是安全边界，它是能力供给层**。安全边界在进程隔离（第 5、6 章）与策略（第 8 章）。把"消息机制容易被改"当成 iOS 的安全问题来讨论是方向性错误；正确的问题是"什么样的输入可以变成行为"。

### 15.6 观测

- **开发者**：列出自身动态能力清单（是否交换方法、动态注册、反射读属性），对每条外部输入抵达这些能力处的路径写测试。
- **审计用途的静态分析**：可确认某应用是否高度依赖动态注册与交换——这类应用行为更难预测、完整性更难判断。对第三方 SDK，"高动态性"应当降低信任权重，而不是被当作高级特性。
- **应急响应**：iOS 上"运行时被改"表现为**进程内**行为异常（功能错位、界面与逻辑不一致），而不是"出现陌生进程"。因此这类事件主要看行为，而非进程清单。
- **用户侧**：无可直接观测项；有效行为仍是"不要让不可信代码进入设备"。

## 16. 进程生命周期与执行时域的治理

### 16.1 机理：iOS 的进程不是"启动后一直存在"

对攻防影响极大、却常被当作性能话题处理的一层，是**生命周期治理**。iOS 与桌面的关键差别是进程存在期由系统按需分配，并带有明确"时域"：前台、后台、挂起、被终止、被唤醒、扩展临时存在。

这套治理不是调度优化，而是安全属性：

1. **驻留时间即攻击面积分**：只在数秒内运行的进程，可被触达的窗口与常驻进程完全不同。
2. **"谁能被唤醒"是策略**：后台唤醒由作业定义、推送到达、定时与位置事件等条件触发，本质上是一份"谁被允许在你不在场时运行"的清单。
3. **被终止不等于被清除**：挂起进程的内存映像、临时状态与文件残留，构成攻防两侧都关心的"死后状态"。

### 16.2 机理：作业定义是一份可读的授权清单

系统服务通过作业定义描述自己：何时启动、被何条件唤醒、失败是否重启、受哪些资源限制。安全语义：

- 每条定义对应一项**长期承诺**，是持久化审计的基础数据。
- 定义的位置与内容变化（新增、修改、路径改变）是强信号，应作为可对比配置项管理，而不是不可见的内部实现。
- 资源限制本身也是防线：内存上限直接压缩"驻留大量数据或工具代码"的可行性。

第三方应用的等价物是**后台执行声明**（需要用途声明与审核）。这是 iOS 上少数"平台强迫开发者说明动机"的机制，因此也是隐私审计中最有价值的信息之一：不合理的后台用途声明，是一个可投诉、可拒绝、可被下架的行为面。

### 16.3 机理：内存压力终止的双面性

按优先级与内存压力终止进程的机制，性质是：

- **正面**：限制不可信代码的驻留能力，压低"长期潜伏 + 缓慢收集"这类恶意软件的收益模型。
- **需关注**：终止顺序按优先级而非身份。被高优先级角色携带的组件（宿主进程内的扩展/插件）会借用宿主的存活预算。
- **取证面**：终止事件与阈值被记录，"某进程反复被终止"是可见规律，"某进程从未被终止"同样是信息。

判断方法很朴素：设备上若出现"某非系统进程长期高存活 + 持续外联 + 与用途声明不符"的组合，就是异常，与它是否签名无关。

### 16.4 机理：挂起/恢复与状态残留

进程挂起时状态被保留，恢复时行为继续。三点安全语义：

1. **解锁状态与挂起进程的组合**：在前台解锁时读过敏感数据的进程被挂起，其内存内容仍在；锁屏不改变它的存在。这解释了第 2.4 节"解锁窗口"为何是真实边界。
2. **恢复路径的信任**：应用从保存状态恢复时，常把持久化内容重新当作"可信的当前状态"。若该内容位于多方可写容器（第 8.3 节），恢复路径本身就是被污染的入口。
3. **快照与截图**：进程切换时系统保存界面快照用于动画与恢复。语义上：**屏幕上出现过的内容会在文件系统里留下一张图像**。这是生命周期与数据保护的交叉点，也是第 18 章处理的问题。

对开发者可合并成一条纪律：**敏感界面退出前台时主动遮盖；状态恢复时重新校验持久化内容；不要把"上次是对的"当作"这次也对"的依据**。

### 16.5 机理：扩展与"借用宿主身份"

扩展让代码在其他进程上下文运行，并把生命周期与身份解耦。安全语义：

- 扩展有独立沙盒，但**与宿主共享数据容器**：第 8 章三层授权的交集在此给出结论——扩展边界是能力边界，不是数据边界。
- 宿主被唤醒时，扩展的短暂执行窗口一并被唤醒。攻击者不需要自己获得后台配额，只需被装进一个合法宿主。
- 共享容器内的写入是"跨进程传递行为"的低门槛形式（第 15.3 节 (b) 类的现实入口）。

因此"是否允许某个第三方组件进入我的进程/容器"应按**能力授予**级别决策，而不是按"它有没有被签名"。

### 16.6 保证与边界

| 性质 | 强度 | 边界 |
|------|------|------|
| 第三方不能随意常驻后台 | G1（需声明与审核） | 借用宿主身份可间接获得执行窗口 |
| 唤醒条件明确可审计 | 观测友好 | 普通用户可见度低，多在备份与诊断包内 |
| 内存上限压缩驻留能力 | G2 | 对寄生在高优先级宿主内的组件无效 |
| 挂起状态受数据保护约束 | G1 | 解锁窗口内的内存内容不在保护范围 |

### 16.7 观测

- **普通用户**：可查的是"哪些应用声明了后台模式"（商店页面与权限说明）与"哪些应用异常耗电/异常流量"（设置内可见）。这两项看似平庸，却是生命周期治理留给用户的唯一直接观察口。
- **管理侧**：作业定义与配置清单在受管设备与备份中更完整；把"新增自启条目"纳入变更审计，比单点查杀更符合 iOS 现实。
- **应急响应**：把"进程存活时长 + 唤醒来源 + 外联时间"对齐成时间线；无声明的持续存活、无用户操作的周期性唤醒优先排查。

## 17. 配置与状态存储的授权语义

### 17.1 机理：底层支撑里有四类"配置"，性质差异极大

配置存储常被笼统当作"存键值的地方"。按安全语义至少分四类：

| 类别 | 典型载体 | 谁能写 | 保护级别 | 语义风险 |
|------|---------|--------|---------|---------|
| 应用自有偏好 | 沙盒容器内的默认偏好存储 | 仅该应用（同 group 共享） | 受数据保护类约束，但按可读性设计 | 把秘密当配置存 |
| 系统级策略配置 | 签名的描述文件与策略清单 | 受管安装通路 | 签名与安装授权 | 恶意或过时文件改变策略 |
| 安全能力开关 | 系统权限数据库、策略表 | 系统服务 | 特权写 | 直接构成权限边界 |
| 启动与个性化参数 | 启动参数、固件级设置 | 受控工具与恢复通路 | 硬件与签名 | 改变整机运行形态 |

读法：**越靠下，写权限越少、影响越大、可观测性越差**，防守重心按此顺序分配。

### 17.2 机理：默认偏好存储不是秘密存储

偏好存储是"结构化配置"，不是"机密存储"：

- 按应用容器隔离，但**同 App Group 内共享**；容器内文件按可读性设计。
- 与数据保护类交叉：文件级保护确实生效，但"解锁状态下该应用的任何代码都能读到它"是结构性的。
- 备份通路可能把它带出设备，可见性取决于备份类型与端到端保护设置（第 11.4 节）。

正确纪律只有一条：**密钥、令牌、可关联标识进入钥匙串类设施并按可访问级别声明，不进入配置存储**。破口通常出现在"迁移方便"或"共享给扩展"，所以它需要写成 code review 规则，而不是依赖自觉。

### 17.3 机理：描述文件是设备与外部之间最有力的接口

描述文件是**签名配置**，把"允许什么、限制什么、信任什么"写入设备：

- 它是**合法豁免者**：可改变来源限制、安装根证书、配置网络与 VPN、提供托管能力（第 2.4 节、第 12.4 节）。
- 它自带身份链，签发者可追溯，因此比"设备被偷偷改了什么"更可审计。
- 它也是攻击者偏爱的合法外衣：一份安装合法但含义被误读的文件，比一个漏洞更省事。

审计时逐份回答四个问题：谁签发、何时到期、改变了哪几条策略、是否仍需要。成本很低（界面可查），收益很高——它是少数"能一句话改变整机保证等级"的配置项。

### 17.4 机理：根证书与网络信任配置属于同一类问题

设备的信任存储（可参与服务器身份验证的根证书）与网络配置（VPN、加密 DNS、代理）共同构成通信层信任边界：

- **安装一个可解密流量的根证书，等价于把 TLS 校验对象从公链换成"你信的那个签发者"**。加密没变弱，信任集被扩大了。
- VPN 与代理改变流量路径与可见性，其来源常与描述文件挂钩，应纳入第 17.3 节的清单管理。
- 加密 DNS 是双面的：配置可信服务提升隐私，配置错误的服务把查询历史集中给单一第三方。

这一层的可观测性是三章里最好的——用户可直接查看与删除。这正是"把 G1/G3 层的检查做扎实"的具体落点。

### 17.5 机理：状态持久化与安全决策的耦合

一类容易被忽略的设计是**安全决策依赖持久状态**（是否接受条款、解锁失败计数、自动擦除计数、是否已启用某保护）。它们的语义要求高于普通配置：

- 跨重启有效，且不能被未授权写入回滚；
- 位于足够强的数据保护类；
- 具备防重放与防回退设计（第 10.3 节的计数器场景）。

若这类状态被写在普通配置存储里，就存在"用合法写入把安全策略回退到旧状态"的风险。这是典型 G3 缺陷：机制存在、接口存在、纪律没做到。

### 17.6 保证与边界

- **G1**：策略类配置写入需要签名与授权通路，普通应用无法直接改系统权限数据库。
- **G2**：容器隔离使跨应用配置读取不成立，但共享容器与备份通路各削弱一半。
- **G3**：如何区分"配置"与"秘密"完全靠实现——平台无法替开发者判断某个值是不是秘密。

边界要点：**配置存储不提供机密性保证，而策略配置改变的是保证等级本身**。前者按数据泄露问题处理，后者按配置管理问题处理，两条线不能塞进同一张合规检查表。

### 17.7 观测：配置面审计顺序

以下顺序全部落在 V1/V2 档（见第 19 章）：

1. 描述文件清单：签发者、有效期、策略项，逐份。
2. 证书信任存储：非默认可见的根证书，尤其可参与服务器验证的那类。
3. 网络策略：VPN、代理、加密 DNS 的来源与用途解释。
4. 权限数据库：能读屏幕、能注入输入、能全域访问的条目（第 18 章的借用面在此显形）。
5. 每个自有应用：敏感项是否写在配置存储；同 group 共享数据是否含秘密。

## 18. 显示、输入与图形通路的隔离语义

### 18.1 机理：屏幕内容与输入事件都是"有所有权的资源"

最贴近用户、却最少被当作安全层次讨论的，是图形与输入通路。其语义是：

- **显示内容**是合成器把多个来源图层合成后的输出。谁能取得合成前图层或合成后输出，是权限问题，不是技术副作用。
- **输入事件**由系统事件通路分发给"当前接受者"。谁能注入事件，等价于"谁能替用户操作"。

这两句定义了一类高价值权限的真实含义：**读屏幕 = 读到用户当下看到的一切；注入输入 = 以用户身份操作**。它们比"访问某个数据类别"更接近完整账号接管，因为读取的是明文呈现的内容，注入的是合法操作序列。

### 18.2 机理：屏幕捕获是受控通路

底层支撑把屏幕内容获取做成受控能力，三个防守要点：

1. **可感知提示**：合法捕获伴随可见反馈；没有可见反馈的持续捕获是强异常信号。
2. **敏感图层可声明不被捕获**：口令输入、生物特征确认、支付确认类界面走"不可入快照/不可捕获"的表达方式（第 16.4 节的快照残留问题在此被消解）。这不是加密，而是**显示层的策略拒绝**。
3. **跨设备显示延伸需显式同意**：投射与镜像类能力把"本机可见内容"扩到外部接收方，属于信任扩张事件，应与配对、自动连接同类管理。

### 18.3 机理：输入隔离与辅助能力的双刃

系统提供给用户的能力（语音控制、切换控制、无障碍自动化）需要在事件层拥有较强插入能力，形成结构性张力：

- 对无障碍用户这是必需品，不能简单禁用；
- 但"能注入事件"正是其实现机制，因此任何拥有该能力的进程都拥有"以用户名义操作"的等效能力。

防守纪律因此非常具体：**输入类与自动化类能力授予必须按最高风险级别盘点**——它从哪来（用户显式启用还是安装副作用）、什么时候启用（快捷开关是否他人可及）、是否在不当场景长期打开（设备可能离开用户手中）。

### 18.4 机理：GPU 与合成层的隔离语义

图形由独立处理器完成，其工作队列与缓冲区与主内存共享物理介质：

- 跨进程的图形缓冲区是**共享对象**，生命周期与可见性由内核对象模型管理，"谁可以读这块缓冲"是权限问题；历史上图形栈的跨进程共享缺陷正源于此。
- 合成层保留内容的时间取决于实现，第 16.4 节的快照残留即属此类。
- 图形处理器固件属于第 14 章的"独立更新、用户不可见"组件。

这一层的结论偏纪律而非配置：**不要把"只在屏幕上出现"当作安全状态**。屏幕内容会被合成、缓存、快照、镜像、捕获，各环节受策略管辖但都不承诺机密性。真正的机密性必须在数据层（第 2 章）解决，显示层只负责"不在不该出现的地方出现"。

### 18.5 机理：摄像头与麦克风是独占型硬件通路

音视频输入通路的底层性质是**运行时独占 + 状态可被观察**：

- 系统对这些通路的使用有可见指示，这是设计上的物理层提示，应用无法关闭——属于 iOS 上少数接近 G1 强度的隐私保证。
- 使用授权由权限层控制，但**已授权后的持续使用不构成异常**：获得麦克风权限的应用可在其声明场景内采集。防守重点仍是"谁被授予了"（第 17.7 节的权限盘点）。
- 与生物特征通路不同：生物特征的匹配在隔离域内完成（第 3 章，本仓库另有专题），而音视频数据默认进入应用可用范围。两条路径的安全等级完全不同，混为一谈会导致错误的权限判断。

### 18.6 保证与边界

| 性质 | 强度 | 边界 |
|------|------|------|
| 屏幕与输入类能力需显式授予 | G1 | 授予后的合法使用不留异常痕迹 |
| 采集状态对用户可见 | G1 | 用户必须知道"可见"这件事本身 |
| 敏感界面可声明不可捕获 | G2 | 依赖应用正确声明，未声明即无保护 |
| 跨设备显示需同意 | G1 | 同意是一次性事件，长期保留后易被遗忘 |
| 图形共享对象的跨进程隔离 | G1 | 由内核对象模型管辖，非应用可控 |

### 18.7 观测

- **用户**：把"读取屏幕内容"与"注入输入"类项目从权限清单里单列复核，不与普通数据权限混判；检查无障碍与自动化开关的启用来源；对"没有可见指示却持续出现的采集"按事件处理。
- **开发者**：口令、支付、身份确认类界面主动声明不可入快照；不要依赖"我很快清掉了"来控制屏幕残留。
- **应急响应**：显示与输入类证据在诊断包里最完整（合成、捕获、权限变更、指示历史），现场采集优先级高于常规判断。

## 19. 可观测性：如何在本机验证保证是否生效

### 19.1 为什么"观测栏"是这份报告的落点

前面十八章的每一条保证，如果无法验证，就只是文档承诺。本章把可验证性分成三档，并给出可执行的检查节奏。这是本报告与"子系统巡览型"文档差别最大的部分：**目标是让读者能回答"我现在这台设备上，哪一层是活的"**。

| 档位 | 谁能看 | 典型内容 | 局限 |
|------|-------|---------|------|
| V1 用户可见 | 设置界面 | 系统版本、锁定模式、开发者模式、描述文件、配对主机、权限清单 | 显示状态，不显示实现强度 |
| V2 主机/工具可见 | 与主机配对或使用配置工具 | 崩溃与诊断文件、部分配置、备份内容 | 需要物理/半物理访问，受保护类限制 |
| V3 取证包可见 | 备份解析或取证环境 | 持久化条目、时间线、日志聚合 | 依赖备份时机与类型；不保证完整 |

### 19.2 一份"信任状态基线"检查表

建议把它当成例行流程，而不是排查异常时才做。以下项目全部可在 V1/V2 档完成：

**基线 A：执行链与来源**

1. 系统版本是否为最新（缓解与吊销都在版本里）。
2. 是否存在待生效的安全响应组件（重启节奏）。
3. 开发者模式：应为关闭，除非明确理由。
4. 已安装描述文件清单：逐条能解释用途与责任人。
5. 非 App Store 来源应用：数量、签名身份、是否仍在使用。

**基线 B：能力与授权**

6. 权限清单逐项审查：位置（含精确位置）、麦克风、相机、联系人、照片、健康、蓝牙、本地网络。
7. 特别关注"能读取屏幕/输入"类与"能访问全部相册"类授权。
8. 检查是否有应用长期持有异常高的权限组合（与它的功能不相称）。

**基线 C：连接与信任扩张**

9. 已配对主机清单（清除不再使用的）。
10. 自动加入的 Wi‑Fi 与配对蓝牙设备清单。
11. 网络层：加密 DNS 配置、VPN 配置来源、描述文件是否安装了根证书（尤其是可解密流量的根证书）。
12. 跨设备能力（接力、通用控制类、屏幕镜像类）是否在不需要时被关闭。

**基线 D：痕迹与异常**

13. 崩溃/诊断记录中的完整性类终止（签名、页失效、控制流保护失败）。
14. 系统时间与时区是否与实际一致。
15. 数据"异常干净"：历史消息、照片时间线、日志是否有断档。
16. 电池与流量的异常规律（后台持续活动）。

### 19.3 把检查落到"哪一层保证被验证了"

上述每一条对应的层次，是这张映射表的意义：

| 检查项 | 验证的保证 | 强度 |
|-------|-----------|------|
| 系统版本与待生效组件 | 升级通路及时、缓解覆盖 | G1/G2 |
| 描述文件、企业应用来源 | 签名与能力授予链 | G1 |
| 开发者模式状态 | 本机是否主动放宽完整性约束 | G1 |
| 权限清单 | 授权层（TCC）实际授予范围 | G1 |
| 根证书/VPN/DNS 配置 | 网络信任边界 | G1/G3 |
| 已配对主机 | 调试/观察能力扩张面 | G1 |
| 完整性类终止记录 | 缓解措施确在拦截 | G2 |
| 时间线断档 | 是否发生过恢复/刷机 | G1 |

注意这张表的最后一列：绝大多数检查项验证的是 **G1 与 G2 是否被削弱**，而不是"验证 G0 有效"。G0（硬件信任根）在设计上不提供用户可查的证据通路，这是正确的：能随便证明"我的硬件没被换过"的系统，反而更容易被社会工程利用。

### 19.4 频率与自动化建议

- **每日**（高价值目标）：锁屏时长与 PIN 策略习惯；不安装新来源；不需要时关闭无线能力。
- **每周**：V1 档快速过一遍基线 A/C；关注更新提示。
- **每月**：完整基线 A–D；做一次诊断采集留存（作为时间线基线）。
- **每季**：审查权限与描述文件的责任人；清除历史配对；复核备份与端到端保护设置是否符合当前风险偏好。
- **触发式**：收到陌生配对/信任提示、出现完整性类终止、被钓鱼点击后立即做全量采集与凭据轮换。

## 20. 薄弱保证排序与攻防结论

### 20.1 按"实际被跨越的频率"重排保证强度

这是本报告希望交付的核心判断。排序依据是公开安全研究与厂商披露的案例分布，而不是机制的优雅程度：

| 排名 | 最常被跨越的层 | 原因 | 防守性价比 |
|------|--------------|------|-----------|
| 1 | **授权与来源治理（G3/G1）** | 用户同意即可合法访问；签名的应用照样作恶 | 最高：改配置就能收紧 |
| 2 | **实现纪律（IPC 校验、解档、路径处理）** | 系统给了工具但不强制使用；缺陷是常态 | 高：代码审计与接口契约 |
| 3 | **近场/连接通路（配对、自动连接、配件）** | 信任扩张事件不被感知 | 中高：清单化清理 |
| 4 | **解释器与可执行内存豁免进程（G2 削弱）** | 设计允许，缺陷即原语 | 中：减少暴露面（锁定模式） |
| 5 | **信息原语泄露 → 抵消随机化** | 单项不致命，组合致命 | 中：更新与减少并发不可信代码 |
| 6 | **控制面（页表、代码加载，G1）** | 已被搬出内核，直接突破成本极高 | 低（对攻击者）；这层是 Apple 的主场 |
| 7 | **硬件信任根与密钥层级（G0）** | 结构上几乎不在软件层可越 | 极低：不要指望攻击者从这里进 |

结论性表述：**iOS 的底层支撑把"难的地方"做得极好，把"依赖人的地方"留给了生态**。防守方投入应集中在后半张表（用户与实现层），而不是试图加固前半张表。

### 20.2 三句可以直接用的判断

1. **一个原语"存在"不等于它"被使用"**：iOS 提供了难以伪造的调用者身份、明确的 CSPRNG 接口、secure coding 约束、数据保护类；每一项都需要开发者主动用对。审计应默认从"这些有没有被用"开始。
2. **缓解措施的价值在组合，失效也在组合**：单独 ASLR、单独 PAC、单独分配器加固都不是防线；一次有限信息泄露或一次有限写入就能把多层同时削弱。因此**"限制读原语"和"限制早期可执行面"比"更多检测"更有效**。
3. **可观测性是被设计削减的，不是遗漏**：动态跟踪类能力在移动平台上不可用，是为了让攻击者也无法使用。防守方案必须建立在"痕迹少"的前提上：靠版本节奏、来源治理、权限清单和异常表征做判断，而不是指望像桌面那样随时抓现场。

### 20.3 演进方向（研究/产品化中，勿当现网防线）

以下属于可能被后续版本采用的底层支撑演进，标注为方向而非事实：

- **更细粒度的硬件级内存安全**（标记/类型化内存一类）逐步扩大覆盖范围；它的意义是把"越界写"本身从可利用原语降级。
- **内核代码的内存安全语言化**（驱动与新组件使用内存安全语言）——Apple 公开讨论过内存安全在内核组件中的推进节奏，属于长期工程。
- **微内核化重构方向**（学术界公开的替换内核实验）——研究性质，不代表近期产品。
- **后量子密码原语进入设备通路**（密钥协商与固件升级通路逐步引入混合方案）——过渡期内既有收益也有实现风险。
- **端侧智能带来的新执行环境需求**：更多计算被放进隔离域与专用加速路径，其安全语义是"新的能力授予面 + 新的可观测盲区"。

### 20.4 结语：把"底层支撑"翻译成防守语言

如果只能留一句话给这份报告：**iOS 的底层技术支撑之所以有效，不是因为每一层都不可破，而是因为它把"必须同时破好几层"变成了默认条件**。防守方的对应策略也因此清晰——不要试图重复加固硬件与内核，而是确保自己从不提供"跳过某一层"的便利：权限不超额授予、来源不放宽、调试与配对通路及时清理、实现层严格校验调用者与输入、更新保持最新。这五项都是用户或开发者可以完全掌控的事，也正是攻防统计中真实失守的位置。

| 设备密钥层级 | 密钥在 SEP/加密引擎内，逐级封装上层密钥 | G0 | 解锁窗口内密钥可用 | 无法直查；关注恢复/迁移提示 |

| 执行域划分 | 映射权与代码加载权搬到内核之外 | G1 | 老机型覆盖不齐；不防越界读写 | 机型+版本对照官方文档 |
| 代码签名与 AMFI | 运行期页级校验 + 能力授予 | G1 | 开发者模式、JIT 豁免、企业分发 | 版本、描述文件、来源清单 |
| 库校验 | 限制可加载的外部代码身份 | G2 | 显式关闭即无 | entitlement 清单审查 |
| ASLR | 地址布局随机化 | G2 | 信息泄露即抵消 | 保持更新；无用户可查项 |
| 指针认证 | 控制流目标合法性校验 | G2→G1 | 合法指针被借用 | 完整性类终止记录 |
| 分配器加固 | 破坏堆元数据的成本上升 | G2 | 竞争/复用绕过 | 崩溃分类统计 |
| audit token | 内核提供不可伪造的调用者身份 | G3 | 服务端可"忘记校验" | 开发者测试非白名单调用者必须失败 |
| XPC/NSXPC | 远端调用与序列化 | G3 | 类型接受过宽、解档风险 | 接口审计、白名单测试 |
| 沙盒 profile | 默认拒绝 + 显式例外的资源策略 | G1 | 例外组合形成间接路径 | 容器结构、备份内容 |
| TCC 授权 | 个人数据类别的用户同意 | G1 | 同意即合法；不覆盖其他资源 | 权限清单逐项审查 |
| 崩溃/统一日志 | 终止原因与结构化痕迹 | 观测 | 轮转、脱敏、级别可被改 | 诊断采集、完整性类终止计数 |
| sysdiagnose | 物理触发的大规模状态快照 | 观测 | 隐私披露量大 | 作为时间线基线留存 |
| CSPRNG 与标识随机化 | 硬件熵 → 内核 → 系统 API | G1 | 开发者自行生成可预测标识 | 代码审计；检查"稳定却随机"的标识 |
| 双轨时钟 | 单调时间不受用户改动 | G1 | 应用只信墙钟 | 改时间测试策略是否被绕过 |
| 文件系统（APFS） | 写时复制、快照、克隆 | G1（一致性） | 不提供篡改证明 | 时间点比对、备份基线 |

| 开发者模式 | 显式放宽本机可执行/调试约束 | G1（削弱） | 开启即降级评估 | 设置 → 隐私与安全性 |
| 设备配对 | 主机获得观察与控制能力 | G3 | 公共/借用主机残留 | 已配对清单 |
| 外设固件与 DMA | 独立代码 + IOMMU 限制可达范围 | 信任型 | 用户不可见 | 只能靠更新与锁定模式 |
| 无线接入 | 连接即能力授予 | G1 | 自动连接、旧制式 | 网络/蓝牙清单 |
| 对象运行时 | 消息按数据（名字/类表）在运行期决定 | G3 | 不是安全边界；外部输入抵达反射即失效 | 动态能力清单；输入是否进入按名解释接口 |
| 生命周期治理 | 存在期、唤醒条件与资源上限由系统分配 | G1 | 借用宿主身份可间接获得执行窗口 | 后台用途声明、耗电与流量、自启条目变更 |
| 配置与状态存储 | 四类载体按"写权限越少影响越大"分层 | G1/G3 | 配置存储不承诺机密性 | 描述文件、根证书、网络策略、权限库清单 |
| 显示与输入通路 | 合成与事件分发是受控能力，非副作用 | G1/G2 | 授予后合法使用不留异常；未声明即无捕获保护 | 屏幕读取与输入注入类授权单列复核 |

**每天做**：不装来源不明的东西；不需要的无线能力关掉。
**每月做**：权限清单、描述文件、已配对主机、非商店应用四项清账；做一次诊断采集留存。
**立刻做**：出现陌生信任提示或完整性类异常终止 → 采集 + 更新 + 凭据轮换。
